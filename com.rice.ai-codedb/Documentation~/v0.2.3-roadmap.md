# UnityCodeDB v0.2.3 Roadmap

Status: approved plan; implementation not started.

## Summary

v0.2.2 third-party acceptance confirmed that cross-elevation coordinator
queries, C# and Shader/HLSL regex forwarding, bounded reads, lifecycle recovery,
and BatchMode isolation work on a representative third-party project. The same
acceptance exposed three remaining product gaps:

1. Updating the Unity Package while MCP and watcher leases are active leaves
   the tracked host payload on the previous version. A user must pause the
   watcher, disconnect every MCP owner, authorize Sync, and recreate sessions.
2. Closing Unity correctly stops the project backend, but reopening Unity does
   not recreate a closed project MCP transport inside the same Codex session.
3. The Manager exposes one small unlabeled automatic-refresh toggle, but no
   explicit manual Start and Stop commands with distinct runtime semantics.

v0.2.3 is a bounded lifecycle and upgrade release. It introduces immutable
host generations, automatic safe package upgrades, request-boundary handoff,
same-client recovery after Unity restarts, explicit manual controls, and
truthful migration status. It does not add Discover Read tools or change the
v0.3.0 query-expansion scope.

The target release identity is package `0.2.3`, payload `poc.22`, sequence
`22`. Those values advance together only when the implementation is ready for
release validation.

## Product Contract

- A normal package update requires no watcher pause, MCP disconnection, Sync,
  service restart, PID management, or lease cleanup by the user.
- A lease protects only the generation that owns it. It does not prevent a new
  generation from being installed or selected.
- Active requests finish on the generation that accepted them. A request never
  observes files from two generations.
- The final interactive Unity Editor stops the project-owned coordinator,
  Provider, adapter worker, and watcher. BatchMode never creates that demand.
- A Codex-owned thin stdio bridge may remain dormant while Unity is offline so
  the same client session can report `EDITOR_OFFLINE` and reattach after Unity
  returns. The bridge does not own Editor demand, run a Provider, write an
  index, or keep a watcher lease.
- CodeDB never kills Unity, Codex, or MCP processes to complete an update.
- Automatic behavior is the default, while explicit manual Start, Stop,
  Restart, Sync, Repair, and rollback-oriented diagnostics remain available.
- Generated generations, pointers, leases, staging data, logs, and rollback
  evidence remain project-local, ignored, disposable, and credential-free.
- First adoption, Remove, downgrade, unowned targets, staged managed bootstrap
  changes, and user drift continue to fail closed behind explicit review.

## Architecture Decision

### Stable Bootstrap And Immutable Generations

Keep one small project-owned bootstrap at the existing registered wrapper path.
The bootstrap owns MCP framing, project-root validation, output bounds, and
generation selection. Version-specific implementation files live in immutable
directories under the existing ignored project-runtime boundary.

Conceptual layout:

```text
AIWork/
  codedb/
    wrapper/codedb-project-wrapper.mjs       stable audited bootstrap
  .runtime/codedb/
    host/current.json                       atomic generation pointer
    host/generations/poc.22/...             immutable implementation
    host/staging/<transaction-id>/...       incomplete candidate
    host/leases/<generation-id>/...         generation-scoped owners
```

The exact provider slug and existing runtime-root conventions remain intact.
The layout must not create a machine-global cache or scan another project's
runtime.

`current.json` records package version, payload version, sequence, complete
manifest identity, bootstrap protocol, and the selected generation directory.
It is published only after staging validation succeeds. The stable bootstrap
is changed only for a reviewed bootstrap-protocol migration, not for every
payload revision.

### Request-Boundary Handoff

Each request resolves and pins one generation before dispatch. A generation
lease remains valid until that request completes. After an atomic pointer
change:

1. in-flight requests finish on the old generation;
2. new requests load the new generation through a cache-safe module identity;
3. the old implementation is disposed only after its request and process lease
   counts reach zero;
4. transport continuity does not depend on Codex respawning a terminated MCP
   process.

The bridge must keep disabled, Editor-offline, starting, stale, and unreachable
states read-only with `provider_attempts: 0`. It may attach only to an
authenticated Editor-owned coordinator and must never restore a one-shot
Provider fallback.

### Unity Backend Ownership

The Unity lifecycle owns the coordinator, Provider, Shader/HLSL adapter, and
watcher. Same-project Editors share one backend through session leases. A
project-scoped update lock elects one updater and one watcher handoff owner.

Closing the final Editor releases backend demand and stops every backend
process. The dormant client bridge is not counted as backend demand. When an
interactive Editor returns, its new lease starts the backend and the existing
bridge reattaches on the next bounded status or query attempt.

### Manual And Automatic State

Separate persistent policy from immediate runtime commands:

- `Start with Unity Editor`: persistent toggle, enabled by default after Setup;
- `Start now`: session-scoped immediate start while an Editor is online;
- `Stop now`: session-scoped suppression that reconcile cannot immediately
  undo; it ends on `Start now` or the final Editor shutdown;
- `Restart`: graceful stop and start with readiness verification;
- `Automatic host updates`: persistent toggle, enabled by default for owned,
  unmodified upgrades;
- `Update now`, `Verify`, `Repair`, and `Remove`: explicit maintenance actions
  with their existing safety boundaries.

The existing persistent paused marker migrates to automatic-start disabled.
The UI must state whether an action changes persistent policy or only the
current Editor session.

## Scope

### Automatic Safe Host Upgrade

1. Detect package, payload, or bootstrap-protocol drift after package refresh
   without requiring the Manager window to be open.
2. Acquire a project-scoped update lock and re-evaluate ownership after the
   lock is held.
3. Treat a package update as authorization only when every previously managed
   bootstrap target is still owned, byte-exact, unstaged, and at a lower known
   sequence.
4. Copy the candidate generation into a same-volume staging directory, verify
   the manifest, target allowlist, hashes, syntax, root boundary, and protocol,
   then atomically publish the immutable directory.
5. Switch `current.json` only after validation and keep the last known-good
   pointer available for rollback.
6. Preserve explicit authorization for first adoption, Remove, downgrade,
   drift, unowned targets, staged bootstrap changes, and payload collisions.

### Generation-Scoped Lease And Cleanup

1. Include generation ID, process identity, process start identity, owner type,
   project root, and heartbeat in every new lease.
2. Permit install and pointer switch while old MCP or watcher generations have
   live leases.
3. Refuse overwrite, Remove, or garbage collection only for the generation
   that a valid lease owns.
4. Reclaim only provably dead or identity-mismatched stale leases.
5. Retain the current generation, the last known-good generation, and every
   live leased generation. Apply bounded age/count cleanup only to the rest.

### Watcher Handoff And Multi-Editor Coordination

1. Quiesce the old watcher at a safe boundary before a new generation becomes
   the sole index writer.
2. Start and verify the new watcher after the pointer switch; never allow two
   generations to write the same index concurrently.
3. Roll back the pointer and restore the old watcher when new watcher readiness
   fails.
4. Make every same-project Editor observe the elected update state instead of
   starting a competing migration.
5. Keep different Unity projects on independent pointers, leases, update
   locks, backends, indexes, and logs.

### v0.2.2 Bootstrap Migration

1. Recognize the flat `poc.21` installation as a named legacy generation.
2. Install `poc.22` beside it without overwriting scripts that a legacy process
   may invoke after startup.
3. Atomically migrate the owned, unmodified registered wrapper path to the
   stable bootstrap.
4. New MCP transports use `poc.22` immediately. Already-running v0.2.2
   wrappers remain identified as `legacy-draining` until their client sessions
   end naturally; they are never killed automatically.
5. Do not claim same-process hot handoff for a legacy wrapper that was started
   before the stable bootstrap existed. Seamless request-boundary handoff is a
   contract for transports started through the v0.2.3 bootstrap.
6. Remove the flat legacy generation only after all legacy leases are gone and
   ownership still matches the recorded snapshot.

### Manager Controls And Status Truth

1. Replace the unlabeled automatic-refresh toggle with a labeled persistent
   policy control and explicit Start, Stop, and Restart commands.
2. Keep controls at stable dimensions in Overview and Index layouts and expose
   clear disabled reasons when an action is unavailable.
3. Report `INSTALLING`, `SWITCHING`, `DRAINING`, `CURRENT`, `ROLLBACK`,
   `CONFLICT`, and `CHECK_FAILED` separately.
4. Show package, selected generation, watcher generation, bootstrap protocol,
   and legacy session count.
5. Show every live owner or an aggregate count with expandable owner details;
   never present only the first PID as the complete blocker set.
6. Replace misleading "can be synchronized" guidance when live state requires
   migration, draining, or explicit conflict resolution.
7. Keep Manager observation and refresh read-only. Automatic upgrade is owned
   by package lifecycle reconciliation, not by opening the window.

## Hard Gates

| Gate | Release condition |
| --- | --- |
| Windows and Unity support | Unity 2022.3 on Windows passes normal and cross-elevation lifecycle matrices. |
| Project isolation | No pointer, lease, generation, process, index, or result crosses project roots. |
| Atomicity | A crash at every staged mutation boundary leaves one complete selected generation and recoverable journal evidence. |
| Active-request safety | No request observes mixed generations or is terminated for upgrade. |
| Client continuity | Unity close/reopen and a post-v0.2.3 generation switch work in the same Codex session without transport recreation by the user. |
| Backend lifecycle | Final Editor shutdown leaves no coordinator, Provider, adapter, watcher, or Editor-demand lease. |
| Mutation boundary | Automatic upgrade touches only owned, unmodified bootstrap targets and ignored generation state. |
| Rollback | Failed validation or watcher readiness restores the last known-good pointer and usable backend. |
| Manual control truth | Persistent policy and immediate Start/Stop/Restart semantics are distinct, visible, and tested. |
| Baseline preservation | v0.2.2 query correctness, regex, bounds, no-fallback behavior, and BatchMode isolation remain green. |

## Acceptance

1. Starting from v0.2.2 with Unity, one watcher, and multiple MCP leases active,
   updating the package installs and selects v0.2.3 without a manual pause,
   disconnect, Sync, process stop, lease cleanup, or service restart.
2. An in-flight request completes on its pinned generation while the next
   request through a v0.2.3 bootstrap uses the new generation with no MCP
   transport failure.
3. A pre-existing v0.2.2 wrapper remains usable and visibly
   `legacy-draining`; new sessions use v0.2.3, and legacy cleanup occurs after
   natural disconnect without user action.
4. Closing the final Unity Editor stops every Unity-owned backend process.
   Reopening Unity lets the same Codex session return from `EDITOR_OFFLINE` to
   successful queries without restarting the task.
5. Automatic-start and automatic-update toggles persist independently. Start,
   Stop, and Restart commands perform their documented immediate behavior and
   are not silently reversed by reconcile.
6. Two same-project Editors share one backend and one updater; final-lease
   shutdown remains correct. Two independently configured projects remain
   fully isolated while running concurrently.
7. Normal Unity plus normal MCP and elevated Unity plus normal MCP both pass
   status, exact C#, regex C#, bounded read, and Shader/HLSL query checks.
8. Existing v0.2.1/v0.2.2 runtime configuration is either valid or reports an
   explicit upgrade requirement and regenerates only through its reviewed
   runtime path.
9. Injected staging, pointer publication, lease publication, watcher startup,
   cleanup, and Unity-crash failures all preserve or restore a usable complete
   generation.
10. BatchMode completes project initialization with zero Editor lease and zero
    backend process. Domain Reload, Play Mode, normal close, cold restart, and
    forced-Editor recovery remain green.
11. Manager controls and every migration state pass floating, docked, minimum
    width, disabled, long-path, and multi-owner visual acceptance.
12. A third-party project validates the complete v0.2.2-to-v0.2.3 upgrade and
    same-session Unity restart path before stable promotion.

## Delivery Sequence

1. Freeze the generation manifest, pointer schema, bootstrap protocol, lease
   schema, and persistent/manual state model.
2. Build fail-injection fixtures for staging, atomic pointer publication,
   generation leases, cleanup, rollback, and flat-layout migration.
3. Introduce the stable bootstrap and dormant offline bridge behavior without
   changing the existing Discover Read tool surface.
4. Add request-boundary generation pinning and implementation disposal.
5. Add automatic package reconciliation and v0.2.2 flat-layout migration.
6. Add single-writer watcher handoff and same-project update election.
7. Add Manager policy toggles, Start/Stop/Restart commands, migration states,
   and complete owner diagnostics.
8. Run syntax, package boundary, payload hash, materializer, EditMode,
   lifecycle, permissions, migration, failure, multi-Editor, two-project,
   BatchMode, and third-party acceptance.
9. Advance version, payload sequence, changelog, documentation, and release
   artifacts together only after every required gate passes.

## Out Of Scope

- New tree, symbol, outline, callers, dependency, explore, semantic context,
  batch, or controlled dependency-lane tools; those remain v0.3.0 work.
- A global CodeDB daemon or machine-wide generation store.
- Automatic Provider acquisition or one-shot Provider fallback.
- Killing Unity, Codex, or MCP processes to force an upgrade.
- Automatically resolving user drift, staged managed bootstrap files, unowned
  files, downgrade, or payload identity collisions.
- Rewriting or moving published v0.2.1 and v0.2.2 tags.
