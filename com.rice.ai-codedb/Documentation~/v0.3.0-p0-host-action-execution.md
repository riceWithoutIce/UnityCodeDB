## Purpose And Boundary

One Manager-initiated Host or dependency action must have one attributable
admission, execution, result, and visible terminal state. The user must be
able to distinguish a command that completed from a product that is Ready.
This contract covers the Manager action envelope, Package-owned Host payload
commands, and Configure Dependencies. It also constrains neighboring Manager
commands that share that envelope. It does not replace Supervisor query-first
scheduling, Provider installation authority, activation/retirement contracts,
or the materializer's mutation authorization.

## Execution And Terminal Result

1. A click is either rejected without work or admitted once with an action ID,
   captured execution context, effect class, and authorization source. A
   second click cannot create a competing owner while the first is active.
2. UI shows bounded progress for the admitted action. Only the main thread
   touches Unity UI. Worker progress is data, not a Unity API call.
3. The command result retains its actual exit code, stdout, stderr, timeout,
   elapsed time, and structured action outcome when available. A failed
   result is not replaced by a generic synthetic failure. Missing or invalid
   structured evidence is identified as such; it is never interpreted as
   success.
4. Post-action status is a separate observation. `exit 0` for DryRun means
   the diagnostic command ran, not that Installed, Configured, or MCP Available
   is current. Conversely, a non-Ready state must retain any successful
   command evidence and explain the remaining product condition.
5. Every admitted action reaches a visible terminal classification when
   authenticated evidence exists: completed with Ready, completed with Needs
   Attention, failed, timed out, or cancelled. Without that evidence, show an
   explicit unresolved command outcome instead of inventing a terminal. A
   progress indicator must not remain active after terminalization.
6. A timeout, Manager close, compilation, Domain Reload, or Unity shutdown
   cannot silently authorize a second action or claim a mutation was rolled
   back. On return, observe the existing owner/journal and show a bounded
   pending or recovery state until the authoritative outcome is known. Do not
   stop an external process merely to close the UI.

## Fail-Closed Rules

- The backend rechecks mutation authority at the point of effect. A stale
  Manager cache, successful preflight, or human confirmation alone cannot
  override a changed selection, invalid closure, live/ambiguous holder, or
  out-of-scope target.
- Unknown, conflicting, or incomplete command/operation evidence remains
  unresolved with a specific reason. It never becomes a successful command
  through an `exit 0`, a stale cached snapshot, or a fallback message. Current
  product readiness is classified independently under the Status, History,
  And Change Admission amendment below.
- One action must not merge command output or product status from different
  project, Package, owner epoch, or operation identities.
- Read-only inspection must not mutate project state. Any action that writes
  availability, leases, journals, or configuration is declared with its
  actual effect class and tested accordingly.

## Status, History, And Change Admission Amendment

An old Manager action with durable admission and claim but no authenticated
terminal or proven pre-effect refusal has a permanently unknown command
outcome unless authentic evidence for that same action later appears. Current
product status and permission for a future project change are different
questions. Neither is answered by rewriting the old command history. This
amendment applies to the current S25 Install block and future actions with
the same evidence shape; it does not reinterpret or erase the S27 historical
Remove disposition.

| Question | Authority and visible result |
| --- | --- |
| What happened to the old action? | Preserve its exact admission, claim, identity, and `CommandOutcomeUnknown`; show an explicit historical warning. Never synthesize a terminal/pre-effect receipt, infer no effect, or automatically replay it. |
| What is the product state now? | Obtain a fresh, authenticated, project-bound read-only status independently of the old action. Manager may display Ready when that status proves Ready, while retaining the separate unknown-action warning. A stale cache, `INSTALLED` selection alone, or Supervisor `core_ready` alone does not prove Manager Ready. |
| May another project change begin? | Perform a new, bounded admission check for the requested action and current project. Ready status and a historical disposition alone are not mutation authority. |

Status observation must remain available even while an old action is unknown;
the old pending entry must not indefinitely force the product-status field to
Needs Attention. The UI must not collapse a current Ready state and an unknown
historical command into one apparent command success or silently hide the
warning. Read-only status must not write availability or project state as a
side effect; any existing effectful probe retains its declared effect class.

Implementation ordering does not couple independent status/history work to a
legacy process proof that its input records cannot supply. A status-first
source change may progress while that proof is unresolved and new mutations
remain refused. Its acceptance is partial for the combined redesign; it does
not establish a safe passing mutation branch or current real-project Ready.

Before a fresh Remove, Install, or other project mutation is admitted, the
worker must authenticate the requested action's project and Package context,
establish that the relevant old writer and any business child capable of this
project mutation are no longer running, and check the current project control
state and operation lock under their owning authorities. Process visibility
that cannot distinguish a live relevant process from a stopped one is
`UNKNOWN` and blocks the change. Recheck the relevant evidence immediately
before the new admission; backend mutation checks still apply at the point of
effect. Never terminate a process to satisfy the gate. A successful gate
permits only a fresh, separately confirmed action under its normal backend
preconditions; it does not certify the old command's result.

The proof scope is the old action(s) relevant to this project and proposed
change, not every historical Package directory or unrelated PowerShell
process. No fixed generation such as `poc.39`, absence of every legacy
removal intent, or globally unique historical Package directory is a
precondition. Project state and intent are evaluated for actual conflict with
the proposed mutation under the owning contract. Retained historical evidence
is not deleted or rewritten. The existing S27 exact-action marker remains a
historical administrative record, not a generic command terminal, status
source, or authority for the next action.

Acceptance must separately exercise: unknown history with fresh Ready and
non-Ready status; status observation without new-action admission; relevant
live, stopped, and unobservable writer/child; project state or lock conflict;
unrelated historical Package/process evidence; changed current generation;
and refusal or acceptance of a fresh action under its ordinary preconditions.
Focused synthetic and source evidence does not replace a separately

## S29 Operation Result Semantics Agreement - 2026-10-08

The user approved this semantic clarification before implementation. It refines

### Field meaning and responsibility

| Evidence or field | Owns | Does not prove |
| --- | --- | --- |
| Authenticated, complete terminal receipt | The recorded command ended with an attributable result | Requested operation succeeded or outstanding effects are safe |
| exit_code and action-specific outcome | Success or non-success of the requested operation; values must agree under the action contract | Current product readiness or absence of effects |
| phase and reason_code | Where the operation ended and why | Independent authority to mutate or clear history |
| mutated_scopes | Recorded scopes changed by this operation | Global project state or effects of another operation |
| cleanup_state | Cleanup completion for the owning operation | Cleanup of every earlier operation or automatic next-action admission |
| Current status snapshot | Current product usability, through the existing status owner | Historical command success |

BLOCKED does not mean that execution never started or no mutation occurred.
The current writer may emit BLOCKED after candidate preparation. FAILED and
BLOCKED must not acquire an invented before/after-mutation distinction in a
consumer. Retain the original value and detail; use phase, reason and effect
fields to explain the actual result. Missing or incomplete authoritative terminal
evidence remains unknown/incomplete, never a known completed failure.

For the bounded historical three-stage case, the permitted non-success shapes
are explicit:

| Stage role | Permitted result shape |
| --- | --- |
| Original Install | Authenticated INSTALL, nonzero matching exit, outcome BLOCKED or FAILED, phase CANDIDATE, exactly host_runtime and instance_candidate scopes, cleanup PENDING |
| Observation | Successful authenticated DryRun, recognized status, no command mutation result |
| Refused Upgrade | Authenticated UPGRADE, nonzero matching exit, outcome BLOCKED or FAILED, phase PREFLIGHT, no mutation scopes, cleanup COMPLETE |

These combinations retain all existing three-stage, argument binding, identity,
terminal flag and output-completeness requirements. The observed producer reason
codes are INSTANCE_CANDIDATE_FAILED and INSTANCE_CONVERGENCE_FAILED respectively;
preserve them for diagnostics and regression coverage. They are not replacement
identity or admission evidence. Other actions and chains retain their own
contracts; this table is not universal acceptance of BLOCKED/FAILED strings.
Zero exit with a failure outcome, nonzero exit with a success outcome, unsupported
outcome combinations and malformed records cannot be converted to success or
accepted through a permissive fallback.

The existing result consumer must provide one shared semantic classification
entry for the affected Install/Upgrade decisions. Callers project this contract
rather than maintain independent outcome lists. The backend publishes facts;
the parser validates the record; recovery interprets the bound stage chain;
the journal and Manager present that interpretation. No new persisted normalized
result, schema, mapping store or competing action authority is introduced.
