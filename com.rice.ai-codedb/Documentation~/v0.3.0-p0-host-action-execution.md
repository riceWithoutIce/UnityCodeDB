# v0.3 Host Action Execution Contract

Status: S22 source baseline accepted; S25 real removal acceptance is blocked
before the business command starts. The S26 amendment below freezes the
control-chain correction. This contract does not authorize a project mutation,
Unity run, Package export, commit, or publication.

## Purpose And Boundary

One Manager-initiated Host or dependency action must have one attributable
admission, execution, result, and visible terminal state. The user must be
able to distinguish a command that completed from a product that is Ready.
This contract covers the Manager action envelope, Package-owned Host payload
commands, and Configure Dependencies. It also constrains neighboring Manager
commands that share that envelope. It does not replace Supervisor query-first
scheduling, Provider installation authority, activation/retirement contracts,
or the materializer's mutation authorization.

## Authorities

| Concern | Owner | Required boundary |
| --- | --- | --- |
| User intent, confirmation, and presentation | Manager on the Unity main thread | No filesystem, hash, process, lock, PowerShell, Node, or synchronous IPC work in open/repaint/tab callbacks. |
| Action admission and immutable execution context | Manager/lifecycle adapter | Capture project and Package identity once; reject overlapping user actions explicitly. Do not recapture a different project or Package inside the worker. |
| External command execution | Worker and Package process runner | Apply bounded timeout/cancellation; preserve the process result. No Unity API, dialog, or progress bar on the worker. |
| Host mutation authority | Materializer and existing Supervisor/instance contracts | Revalidate identity, holder, target, and operation authority immediately before mutation. UI visibility or a prior DryRun is not authority. |
| Product readiness | Authoritative status/reconcile owner | Classify the post-action product state separately from command completion; Manager renders the cached result. |

An action's effect class and authorization source are independent. DryRun and
Verify are observations. Probe may publish operational availability. Upgrade
may perform a lifecycle-authorized mutation without a button confirmation.
Sync, removal, reinstall, and other explicit project mutations require their
existing human confirmation. Configure Dependencies delegates installation
authority to the Provider contract. The implementation task must inventory
each exposed action against this classification; it must not infer that every
unconfirmed action is read-only or that every mutation requires the same UI
prompt.

## Execution And Terminal Result

1. A click is either rejected without work or admitted once with an action ID,
   captured execution context, effect class, and authorization source. A
   second click cannot create a competing owner while the first is active.
2. UI shows bounded progress for the admitted action. Only the main thread
   touches Unity UI. Worker progress is data, not a Unity API call.
3. The command result retains its actual exit code, stdout, stderr, timeout,
   elapsed time, and structured action outcome when available. A failed
   result is not replaced by a generic synthetic failure. Missing or invalid
   structured evidence is identified as such; it is never interpreted as
   success.
4. Post-action status is a separate observation. `exit 0` for DryRun means
   the diagnostic command ran, not that Installed, Configured, or MCP Available
   is current. Conversely, a non-Ready state must retain any successful
   command evidence and explain the remaining product condition.
5. Every admitted action reaches a visible terminal classification: completed
   with Ready, completed with Needs Attention, failed, timed out, or cancelled.
   The classification names the authoritative reason and next supported
   action. A progress indicator must not remain active after terminalization.
6. A timeout, Manager close, compilation, Domain Reload, or Unity shutdown
   cannot silently authorize a second action or claim a mutation was rolled
   back. On return, observe the existing owner/journal and show a bounded
   pending or recovery state until the authoritative outcome is known. Do not
   stop an external process merely to close the UI.

## Fail-Closed Rules

- The backend rechecks mutation authority at the point of effect. A stale
  Manager cache, successful preflight, or human confirmation alone cannot
  override a changed selection, invalid closure, live/ambiguous holder, or
  out-of-scope target.
- Unknown, conflicting, or incomplete command/operation evidence remains
  Needs Attention with a specific reason. It never becomes Ready through an
  `exit 0`, a stale cached snapshot, or a fallback message.
- One action must not merge command output or product status from different
  project, Package, owner epoch, or operation identities.
- Read-only inspection must not mutate project state. Any action that writes
  availability, leases, journals, or configuration is declared with its
  actual effect class and tested accordingly.

## Acceptance

The implementation task should first map every in-scope Manager action to its
effect and authorization source, then repair only demonstrated contract gaps
as one coherent vertical change. Focused source/Editor tests must cover
thread ownership, admission/reentry, result provenance, command-success versus
product-readiness, timeout/reload terminalization, and mutation refusal after
authority drift. PowerShell/Node tests cover the adjacent backend effects.
The exact commit-derived Package then receives one human-owned Unity path:
compile, Manager action, terminal state, tab/Play/Edit stability when Ready,
and normal shutdown. A focused test PASS is not Unity or release acceptance.

Do not broaden this task into Supervisor query scheduling, new Provider
compatibility policy, instance migration, or a full action-framework rewrite
without a new route decision. Preserve protected project and external state.

## S26 Control-Chain Amendment

S25 observed an admitted and claimed direct Manager action without a terminal
receipt. The Package writer performs runtime `Add-Type` compilation after its
claim and before starting the business child. Its failure left Remove CodeDB
Integration unconfirmed; it does not prove that Host Payload removal ran or
that the project is uninstalled. S26 repairs this execution and recovery
boundary as one continuous outcome, without weakening the existing backend
mutation and holder checks.

### Authority And Durable Correlation

- Manager owns human intent, confirmation, and presentation, but its
  `SessionState` is only an Editor-session cache. A project-scoped, Package-
  independent durable action index must preserve the original action ID and
  immutable project and Package identities across Manager close, Domain Reload,
  full Editor exit, and Package-root replacement. The index must bind to exact
  action evidence; it is not mutation authorization.
- The Package-owned one-shot writer remains the default direct-command model.
  It alone may publish its command's terminal evidence. Supervisor-owned work
  retains Supervisor execution authority and exact request/operation lookup.
  Neither route may borrow the other's result or silently fall back.
- Store generated action evidence only under the existing validated user-local
  Manager-action boundary. Do not embed user-specific absolute paths in task
  records. Protect exact project/package/action identity, atomic publication,
  path containment, reparse traversal, and conflicting-record refusal.
- A Package change must not synthesize a new action ID for old pending work,
  silently discard that work, or promote old Package evidence to a current-
  Package result. If old evidence cannot be authenticated, retain the original
  ID and show a blocked, read-only recovery reason.

### Execution And Outcome Contract

- Separate preparation, durable admission, writer claim, possible child start,
  and authenticated terminal observation. Move fallible environment setup off
  the post-claim critical path where feasible. Runtime source compilation or
  dependence on an uncontrolled temporary compiler directory must not be
  required to start an admitted business command.
- Represent proven pre-effect refusal, authenticated command terminal, and
  indeterminate outcome as distinct types or states. An exception, expired
  timeout, absent process, current product status, or missing child marker is
  not by itself proof that an effect did not occur. An exception result must
  not default to authoritative terminal evidence.
- A live writer may publish a bounded start failure only when it can prove the
  child never started. A writer crash between process creation and durable
  observation is indeterminate. Indeterminate work retains the original
  admission and blocks a second owner; there is no automatic replay, cleanup,
  or manual acknowledgement shortcut.
- An authenticated command terminal closes command recovery, then product
  readiness is observed separately. A successful command does not imply Ready
  or `UNINSTALLED / PENDING`; fresh Install remains gated by the authenticated
  uninstall contract.

### Focused Fault Matrix

| Interruption or boundary | Required observation |
| --- | --- |
| Rejection before durable admission | Explicit no-effect refusal; no claimed business execution. |
| Admission exists, writer has not proved child start | Preserve exact ID; report proven pre-effect failure only with evidence, otherwise indeterminate. |
| Writer preparation fails after claim, before child start | No invented command result; a proven start failure may close the command, writer loss remains indeterminate. |
| Child may have started, terminal is absent or writer disappears | Indeterminate; no automatic replay or second owner. |
| Valid terminal, failure, timeout, or output overflow | Exact command result and provenance; product state classified separately. |
| Manager close, compilation, Domain Reload, or full Editor exit | Reattach to the same durable action ID, or retain an explicit unresolved state. |
| Package root or Package identity changes while work is pending | Preserve old ID and evidence boundary; no synthetic ID or cross-Package adoption. |
| Unexpected exception after dispatch or Supervisor response loss | No synthetic authority; exact writer/Supervisor lookup or indeterminate state. |
| Corrupt, conflicting, or missing records | Fail closed with bounded diagnostics; do not infer success from current status. |

Acceptance order is focused synthetic fault injection and directly affected
Editor tests, then an independent review of a stable source snapshot. A
commit-derived Package and one human-owned Unity Remove-to-fresh-Install path
require separate authority. Existing S25 attempts are not replayed. HTTP and
stdio remain future transport research, not prerequisites or a substitute for
durable command evidence. If the one-shot model cannot satisfy this contract
without a new executable, resident service, broader Supervisor authority, or
backend mutation change, stop for structural route reassessment.
