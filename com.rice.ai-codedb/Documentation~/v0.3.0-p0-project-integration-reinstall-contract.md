This contract defines the preview-line recovery route for a project whose
CodeDB integration cannot safely converge across Package versions. It narrows
the earlier [control contract migration design](v0.3.0-p0-control-contract-migration.md):
for this route, `Reinstall CodeDB` means a completed, controlled project
integration uninstall followed by a fresh install. It does not mean an atomic
side-by-side upgrade of the old selected instance. Automatic cross-version
Package upgrades remain deferred until the runtime and control contracts have
stabilized.

## Meaning And Boundaries

- **Project integration uninstall** is an explicit, confirmed CodeDB action
  that deactivates this project's CodeDB selection, registration, and runtime
  ownership, then removes only project-local content whose CodeDB ownership
  and safe removal are proved. It is not removal of the Unity UPM Package.
- **Fresh reinstall** is a separate action after uninstall has reached an
  authenticated terminal state. The current Package creates and verifies a
  new project integration, instance, generation selection, and activation
  evidence under its own authority. It does not reuse, rewrite, or relabel
  the predecessor activation journal as current.
- Removing the UPM Package is optional and separate. Removing it alone does
  not uninstall the project integration. Machine-level Node.js and Provider
  installations are outside both project actions.
- The ordinary user path may present these two actions as one guided flow,
  but it must expose the uninstall result before admitting the install step.
  A partial uninstall is never treated as an empty project.

## Responsibility And Outcome Separation

Manager owns the exact user intent and confirmation; the selected execution
owner owns its command result; the existing project-integration backend owns
resource checks and the serialized uninstall/install transitions. Opening
Manager or observing Ready cannot replace those backend checks. Historical
removal recognition does not introduce another resource writer.

Command completion, logical project uninstall, physical cleanup, current
product readiness, and client tool exposure are separate outcomes. Correctly
restored registration does not prove that an already-open MCP client task has
reloaded it. The client controls that reload; CodeDB does not stop or rebind
the client to satisfy its own operation contract.

CodeDB addresses its own operation effects in this project. This route does
not require Windows restart, a boot checkpoint, global process termination,
generic historical-execution reconstruction, or machine dependency removal.
The exclusion does not allow an unknown active executor or ambiguous project
state to be treated as safe; existing preflight and preservation rules remain.

## One Removal Workflow

User-initiated project uninstall and incompatible-version recovery are two
entry contexts for one project-integration removal workflow. Their Manager
labels and eligibility explanations may differ, but both use the same
ownership classifier, confirmation boundary, durable removal intent,
serialized deactivation transaction, recovery, and cleanup authority.
Historical-control recognition is an input to that classifier, not a second
mutation engine. Neither entry may independently publish `UNINSTALLED`, delete
project records, or assign `cleanup_state` under a weaker contract.

For an incompatible version, `Reinstall CodeDB` is a guided composition of
this confirmed removal and a separate fresh Install. The removal result must
be visible and authenticated before Install is offered or started. A blocked
preflight offers review, not a nominally working Reinstall button. The
ordinary secondary-menu uninstall remains available under the same workflow
when its own ownership preflight passes; the two labels must not appear as
competing ways to remove the same integration state.

## Separate Admission Decisions

Runtime admission asks whether the existing integration can operate under
the current Package. Uninstall admission asks whether the Package can prove
which project-local records and bytes it owns and can remove safely. Runtime
`Needs attention`, including a predecessor selection or an incompatible
activation journal, is neither proof of removability nor a reason to suppress
a separately authenticated uninstall route.

Uninstall preflight is read-only. It inventories the exact selection,
activation/operation records, instance and generation closure, project-local
configuration, and holder/lease evidence. It validates historical records
against their own declared contract and immutable hashes, with required
cross-record bindings. It must not demand that a predecessor generation be
`CURRENT` under the newly imported Package. It must not ignore conflicting
records merely because the old runtime is unusable.

The result has three distinct classifications:

| Classification | Behavior |
| --- | --- |
| Operational | Keep the ordinary runtime path; uninstall still requires explicit confirmation. |
| Not operational, authenticated removable integration | Offer a confirmed project uninstall, with the exact owned scope shown. |
| Unknown, conflicting, redirected, or incomplete ownership | Stop before mutation, preserve evidence, and explain what requires review. |

The currently observed `poc.34` predecessor state is a required fixture for
this classifier, not advance permission to remove it. Its selection,
activation, Supervisor, and holder evidence must be evaluated together. If
their authority cannot be established, the expected result is a clear
fail-closed blocker, not a special-case deletion rule.

## Uninstall Transaction

One serialized project operation performs:

1. Read-only preflight and user confirmation of the exact CodeDB-owned scope.
2. Revalidation of ownership, byte hashes, paths, transaction state, and
   holder/lease state immediately before each mutation.
3. Deactivation of only the proved project integration and its managed
   registration, with recoverable evidence of the intended transition.
4. Removal of exact owned project-local content when no holder requires it.
   Proven live holders retain their immutable instance bytes until natural
   drain. Invalid or ambiguous holders block unsafe physical deletion.
5. Publication of an authenticated `Uninstalled` terminal result only when
   no active selection or project integration authority remains. Explicitly
   retained lease-bound content is inert and identified as pending cleanup;
   it cannot be adopted as a fresh installation.

Logical uninstall and physical cleanup are separate results. `UNINSTALLED /
PENDING` is a valid logical terminal state only after the active selection,
Supervisor authority, and managed project MCP registration have been
deactivated. `UNINSTALLED / COMPLETE` additionally means the exact proved reclaimable
cleanup closure is absent or has been safely reclaimed. A live lease may
delay physical cleanup indefinitely without keeping the old integration
active or forcing the user to wait before fresh installation.

Before removing historical control records, the operation must durably
publish a removal intent bound to its project, state and operation identities,
the exact predecessor selection and activation records, and the immutable
instance/generation closure and holder constraints. The intent survives
successful logical uninstall while any owned cleanup remains. Recovery must
distinguish an uncommitted removal from an authenticated logical terminal
state; neither a missing file nor a bare desired-state flag is sufficient.
Later cleanup may touch only the intent's exact closure, after revalidating
bytes, paths, ownership and holders. Invalid or conflicting intent blocks
cleanup and fresh installation; it never grants general deletion authority.
Holder drain alone does not prove ownership of every mutable file beneath an
old instance directory. Index, adapter, configuration, or other dynamic
content that cannot be individually attributed to CodeDB must not be swept
up by recursive instance deletion. Such content remains inert and pending
until its exact ownership and preservation rules are reviewed.
For the current S24 predecessor, retain the old instance directory and its
index/sentinel bytes byte-exact as an inert closure. Only an individually
authenticated, intent-bound subset may be reclaimed; the existing recursive
retired-instance deletion helper is not authority over the directory.
`UNINSTALLED / PENDING` records the retained closure even after holders drain.
Do not report `COMPLETE` merely because active control records are gone or a
holder exited. A later decision to reclaim further bytes requires a reviewed
ownership rule and matching tests, not an implicit retry of recursive cleanup.

Interrupted removal must recover or stop from durable evidence. It cannot
report success solely because a file is absent, retry in a loop, or proceed
to fresh install with an ambiguous active authority. The user must not be
asked to delete `.runtime` or other state manually to satisfy this contract.

## Fresh Install And User Experience

Fresh install is admitted only from the authenticated `Uninstalled` state,
with no conflicting active control authority. It creates a new candidate
from the current Package, verifies its immutable closure and prerequisites,
and publishes a new committed activation before Manager can report `Ready`.
Failure leaves an honest `Uninstalled` or recoverable in-progress state; it
must not silently restore the predecessor as current.

An authenticated `UNINSTALLED / PENDING` may admit fresh Install when its
retained closure is still inert, bound to the durable removal intent, and
cannot be selected or adopted by the new installation. New activation and
registration must use the current Package's authority; the predecessor's
intent remains available for lease-aware cleanup. An ambiguous or unfinished
removal never admits Install.

The project-local MCP registration has a stable project entry and wrapper
path across this transition. Uninstall disables only its proved CodeDB-owned
keys while preserving unrelated configuration; fresh Install restores those
keys for the newly committed instance, not the old instance or journal.
Neither action rewrites user-global Codex registration or stops existing MCP
clients. Tests prove config and activation bindings without restarting Codex;
the human-owned integration gate uses at most one controlled client reconnect
or new task if the client does not reload project configuration dynamically.

Manager must distinguish `Needs attention - can uninstall safely` from
`Needs attention - removal requires review`. It must not advertise a working
`Reinstall CodeDB` action when the uninstall preflight cannot pass. Opening,
repainting, or switching Manager tabs remains observational and never starts
removal or reinstall. Human confirmation remains required for project
mutations.

## Preservation And Non-Goals

- Never stop Unity, Codex, external MCP clients, or unrelated processes.
- Preserve user-authored project files, unrelated or unknown entries,
  non-CodeDB configuration, and machine-level Provider/Node installations.
  Modify only proved CodeDB-managed project configuration fields, preserving
  unrelated bytes and a recoverable pre-image where required.
- Do not rewrite immutable generations, fabricate an activation, weaken
  fail-closed checks, or use current-Package readiness as removal authority.
- Do not implement automatic cross-version instance upgrades, arbitrary
  historical migration, Provider reinstall, or UPM Package removal in this
  route.

## Instance Manifest Contract And Consumer Closure - 2026-10-07

The instance manifest is a project-integration record, not a machine Provider
manifest. This contract is the single semantic route for its operation-origin
extension. The implementation packet must name its concrete schema/loader
projections; they must agree with this route rather than independently invent
field types. No new registry, executor or general schema service is implied.

The existing optional `originating_action` boundary is:

| Field | Accepted representation and meaning |
| --- | --- |
| `originating_action` | Absent or JSON null carries no origin attribution; otherwise one object containing exactly `action`, `action_id`, and `operation_id`. It is not a stringified object or an activation permit. |
| `action` | A JSON string with the existing exact values `INSTALL`, `UPGRADE`, or `REINSTALL`; accepting an existing attribution value does not introduce an Upgrade user flow. |
| `action_id` | A JSON string containing the originating action's 32 lowercase hexadecimal characters. |
| `operation_id` | A JSON string containing the associated operation's 32 lowercase hexadecimal characters. |

Absence/null semantics preserve the already accepted read boundary, not a new
historical-compatibility or recovery promise. Origin attribution never proves
resource ownership, no integration, verification, current selection or next-
change permission. Keep existing path, hash, identity and effect-point checks.

One producer/consumer map must accompany this change:

- The existing instance backend is the record writer and publishes attribution
  before preparation effects; exceptions must preserve the original association.
- C# instance/control/status readers project the same accepted representation.
- Generation-owned Host readers must decode the same emitted bytes through an
  instance-record entry point, retaining existing bounded strict-JSON checks.
  Do not reuse a flat Provider-manifest parser as the instance schema, weaken
  the Provider contract, stringify origin, or discard it to make parsing pass.
- Inventory the real callers of that entry point. Preparation and watcher
  failure/cleanup are confirmed callers; the implementation map must include
  any other directly coupled readers. A shared reader may be tested once with
  source evidence binding each affected caller to it.

Focused evidence must send a production-emitted attributed manifest through
the target generation's actual Host reader and the directly affected C#
boundary, including the existing missing/null and invalid-origin semantics.
Fixture preparation/availability shortcuts are not this evidence. Prove the
decoding boundary without launching Provider/Unity or touching the real
project; do not add unrelated malformed-input or process-recovery matrices.

If a reader correction changes frozen generation-owned bytes, deliver a
successor through the existing Package identity/materialization authority.
Never edit observed poc.39, its project runtime or the consumed artifact in
place. Exact-artifact byte closure and affected contract-consumer closure
must both pass before a new human session is offered.

A failed attributed candidate with cleanup PENDING is not empty or Uninstalled.
Preserve it and its original failure. Inspection, reconciliation and any new
project mutation retain their separate scoped ownership/effect checks and
human authorization; a new Package or parser PASS alone does not clear it.

## Failed Preparation Removal - 2026-10-07

A failed first Install has its own removal classification within the same
confirmed project-integration uninstall workflow. A project-bound PROVISIONING
candidate with no successful verification is not an Installed selection or a
COMMITTED predecessor. Missing selection does not make its effects disappear.
Direct Manager and Supervisor invocation must carry the actual action and
operation identities before admitted argument hashing. Failure or unknown /
pending completion must not request automatic Upgrade or replay.

For the scoped S29 repair, classify one exact candidate, its original attributed
manifest, immutable generation, known editor lease and host/bootstrap effects.
Validate absence or safe deactivation of selection, active authority and managed
registration; reject conflicting authority, redirected paths or effects outside
the owning declared retention scope.
Do not fabricate a historical Manager-to-backend link that was never recorded.

Reuse the project lock, transaction and removal-intent location. Existing
installed-removal schema v1 remains unchanged. Failed-preparation intent v2
uses authority_kind FAILED_PREPARATION, binds the new removal state/operation,
project and exact retained instance/generation/effect hashes, and omits fictional
selection/activation hashes. Its bounded retained_effects array records exact
project-relative FILE/DIRECTORY entries. The field-level consumer map and
focused evidence are frozen in S29 FAILED-INSTALL-REPAIR-PACKET.md.

Publish durable intent before effects. Authenticated UNINSTALLED means active
integration/registration authority is absent or deactivated; it does not mean
the candidate directory is empty. Preserve the failed candidate and owned
host/bootstrap bytes as an inert PENDING closure. This repair does not grant
recursive deletion or automatic reclamation after holder drain. An explicit
fresh Install may create a different verified candidate while preserving the
bound closure, without adopting the failed candidate as a predecessor or
inventing successful activation evidence. Unproved holder/effect safety remains
a concrete refusal, never implied permission to delete or stop processes.

Source acceptance, artifact delivery and actual project recovery remain separate
evidence classes. The S29 source authorization grants isolated implementation
and review only; real retained-candidate mutation needs its concrete later scope.

### Successive failed Install retention - 2026-10-09

A previously authenticated retained closure may coexist with one newly failed
attributed Install candidate. Distinguish these authorities before classification;
project-wide one-candidate/one-generation cardinality is not the ownership rule.
Unknown additional candidates and conflicting active authority still refuse.
The new candidate's actual production-generated effects must be classified by
their owning contracts and recorded as bounded exact hashes, including known
advanced preparation outputs. No unrestricted directory admission or physical
deletion follows. Live/ambiguous holders and unowned/drifted effects refuse.

Use the existing confirmed project Uninstall, lock, transaction and v2 retained
effect intent. Automatic cleanup cannot retrospectively bind a new unknown
candidate. A Manager action's incomplete historical execution/output is retained
as its original outcome; a separately authenticated current-effects disposition
may establish that the failed candidate is now inert and retained. It binds the
original receipt context and hashes to the committed removal intent and current
holder/authority proof. Marker existence or Uninstalled display alone cannot
release a retained action or authorize fresh Install. Existing resolved-action
index/strict readers project this named FailedCandidateEffectsRetained
disposition; no historical command success, EOF or fictitious activation is made.

The coherent producer/consumer/effect map and narrow source envelope are frozen
in S29 RETAINED-CANDIDATE-RECOVERY-TASK.md. Existing early v2 and installed v1
removal remain supported. This amendment grants no real project mutation,
repeated operational attempt, process termination, OS/session restart or global
configuration change. Source, exact artifact, human and real recovery remain
separate evidence stages.

The stable project wrapper is shared bootstrap authority, not an immutable part
of the failed candidate. Its v2 removal field records the actual authenticated
hash at removal, or explicit absence, separately from retained immutable effects.
An explicit fresh Install may publish its canonical Package wrapper through the
existing bound activation transaction. The exact journal must identify the new
candidate and wrapper pre-image/desired bytes during publication; after commit,
the different READY selection and matching COMMITTED activation own it. Preserve
the old removal observation and all candidate/generation/other retained bytes.
Neither a current-looking file nor a bare desired-state flag proves this handoff.
No separate wrapper replacement executor or historical hash rewrite is allowed.

### Declared Adapter Outputs and Retention Boundary - 2026-10-09

User accepted this design boundary after the real S29 preflight exposed the
production-created adapter directories omitted by the recovery classifier.
This amendment governs retention, not readiness or physical cleanup.

The Text Adapter owns the declaration of candidate-relative
`adapter/text-index/logs` and `adapter/text-index/tmp` as mutable output trees.
Initialization and failed-candidate retention consume one authoritative
declaration through the existing runtime-contract routing. They must not keep
independent copies of these path constants. This is a bounded Adapter contract,
not a generic plugin, directory-permission or filesystem ownership framework.

The candidate identity, original action and generation must be authenticated
before attributing these scopes. A path name alone is not authority. Once bound,
ordinary directories/files beneath the declared trees may be inventoried and
retained without interpreting filenames, log formats or temporary payloads.
Nonempty trees are not a refusal by themselves. An Adapter output manifest is
not required solely to recognize initialization directories/temporary outputs;
it remains required for generated artifacts whose existing contract needs it.
Partial initialization does not imply a successful build or verified instance.

Retention validates containment, no redirected/reparse paths, complete bounded
enumeration/readability, existing process/holder proof and a stable snapshot.
Record project-relative paths, kinds and file hashes in the existing v2
retained_effects intent. The declaration defines scope; the snapshot records
current facts. Revalidate before publication. Changed or unreadable content,
out-of-scope effects or conflicting authority refuse without partial claims of
completion. Keep existing inventory/intent limits; no new file-format matrix.
Refusals identify the affected relative path and concrete cause where available.

This failed-candidate recovery records/preserves effects, deactivates managed
integration authority and publishes the authenticated retained disposition.
It keeps the original Install failed/unknown and cleanup PENDING. A separately
confirmed fresh Install may create a different candidate. It does not execute,
adopt, repair or delete the retained Adapter content, or stop external processes.
Snapshot inclusion confers preservation scope, not proof of each file's creator
or authority for later physical deletion. Later cleanup retains its separate
intent/ownership/holder requirements above; retention admission must not widen it.

Focused acceptance covers actual production initialization topology, declared
nonempty outputs, partial initialization without an Adapter manifest, one
out-of-scope/redirected rejection and existing snapshot-change refusal. Use the
production declaration with the actual recovery entry, rather than maintaining
another handwritten accepted-path list in fixtures. Source, exact Package and
real read-only preflight remain separate gates. No implementation or real
recovery operation is authorized merely by this design agreement.

## Acceptance Boundary

One continuous implementation task should cover the uninstall classifier,
transaction and recovery, fresh-install admission, Manager states, and their
adjacent C#/PowerShell/Node fixtures. Focused tests must cover the observed
predecessor state, valid removal, unknown/conflicting evidence, live and
ambiguous holders, interrupted removal, repeated invocation, and fresh
activation without reusing the old journal. They must also cover durable
intent publication/recovery, pending versus complete cleanup, exact retained
closure preservation and later drain, and project MCP registration removal
and restoration without modifying unrelated keys. A commit-derived local Package
and human-owned Unity golden path are separate gates. This design document
does not authorize code changes, a real uninstall, Unity interaction,
commit, push, or publication.
