## Purpose And Authority

CodeDB provides project-scoped code indexing and bounded read-only discovery,
and manages the project integration and owned runtime resources needed for
those capabilities. It is responsible for its own operations and their project
effects, not for general operating-system recovery or complete historical
execution forensics.

The [v0.3.0 roadmap](v0.3.0-roadmap.md) remains the active requirement source.
This contract clarifies that roadmap's product and authority boundaries; it
does not add capabilities. The [Host Action contract](v0.3.0-p0-host-action-execution.md)
governs command execution and evidence. The
[project integration reinstall contract](v0.3.0-p0-project-integration-reinstall-contract.md)
governs removal, preservation, and fresh installation. Those specific safety
checks remain applicable; this document is not an alternative mutation permit.
An unresolved conflict returns to Planner/User before implementation, not to
a caller-selected weaker contract.

## Definitions

- **CodeDB project integration (项目集成)**: this project's managed CodeDB
  registration fields, configuration, selected Host/instance, and associated
  runtime authority. It is distinct from the Unity UPM Package and from
  machine-level Node.js or Provider installations.
- **Owned resource (自有资源)**: a file, configuration field, or executing
  process whose relevant CodeDB ownership can be established. Directory
  membership, a familiar process name, a bare PID, or an old creation record
  alone does not establish current authority. Ownership does not imply that
  deletion or termination is permitted.
- **Historical operation (历史操作)**: an operation initiated by CodeDB and its
  attributable records, not arbitrary work performed by other software.
- **Command outcome**: what is known about one operation's execution. Preserve
  real results; absent sufficient result evidence, retain an explicit unknown
  outcome rather than manufacturing success, failure, or pre-effect refusal.
- **Current product state**: fresh, project-bound observations of prerequisite,
  integration, configuration, and operational availability. It does not
  certify an old command's outcome.
- **New-change admission**: permission for one requested project mutation under
  its current context, confirmation policy, and resource-owner preconditions.
  Neither a Ready display nor a historical acknowledgement grants it.
- **No integration (从未集成)**: a target-bound classification that no selected
  project integration or conflicting CodeDB effects exist. It is not inferred
  from a missing pointer alone and does not require an invented removal record.
- **Uninstalled (已卸载)**: authenticated logical deactivation of a previous
  integration. It is distinct from no integration and from complete physical
  cleanup; the existing inert `UNINSTALLED / PENDING` rule remains applicable.
- **Candidate attribution (候选执行归属)**: the association of preparation
  resources and execution with their originating project, Package and operation.
  It must exist before candidate effects, not depend on verification succeeding.
- **Activation authority (激活使用权)**: permission to publish a verified
  candidate as the selected integration. Attribution alone does not grant it.

## Constraint Reduction And Shared Semantics - 2026-10-05

Reduce cross-stage prerequisites, not protection of relevant resources:

| Previous or over-broad prerequisite | Aligned rule |
| --- | --- |
| Exact Unity version or machine Editor alias | Recommend `2022.3.x`; record the actual version. No CodeDB version-string admission gate. Concrete API/compile incompatibility remains an evidenced failure, not a claim that every version passed. |
| Removal evidence before a genuinely first installation | Classify no integration and relevant conflicts under the target's ordinary rules; require authenticated removal evidence only for the reinstall route. |
| Candidate is activated/Ready before its preparation ownership can be recognized | Attribute the originating operation before effects; verify before activation. Preparation, verification and activation are distinct phases. |
| Operational Ready before project-integration removal | Use the separately authenticated removal preflight; unusable runtime does not imply either removable or unremovable integration. |
| Every historical command must close before status or another action | Preserve unknown history. Status is independent; mutation admission checks only relevant effects/conflicts and its own resource preconditions. |
| All retained content must be physically deleted before reinstall | Preserve the authenticated inert retained-closure rule. Ambiguous active effects still block the proposed mutation. |
| Every layer reconstructs project/Package identity and its own ownership decision | Reuse one captured action context and attributable links; resource owners still revalidate relevant mutable facts at the point of effect. |

Integration classification, operation progress/outcome and product readiness
are different dimensions. A failed preparation can leave attributed retained
resources without a committed integration; an installed selection can be
non-operational; a failed command does not imply its effects were removed.
Use these meanings consistently without introducing a new serialized state
enum, receipt schema or persistence layer merely to mirror this table.

New-change admission is derived for the requested action, not a fourth
independent ownership authority. The shared context correlates existing
owners; it does not centralize every file writer or grant the execution owner
permission to delete resources or stop processes owned by another component.

Keep exact Package/generation identity and immutable closure, path containment
and reparse protection, managed-key/user-content preservation, one execution
route and result publisher per action, and relevant live/unknown/conflicting
effect refusal. UI readiness or a directory name cannot replace these checks.
No blanket all-history/all-process census, Windows restart, or unproved replay
is added as a recovery prerequisite.

This prospective clarification cannot retroactively attribute the retained
S29 candidate or release the S25/S28 legacy block. Implementation mapping and
any required coupled schema transition need the same-S29 frozen repair scope.

## Product Responsibility Matrix

| Domain | Required CodeDB responsibility | Excluded responsibility |
| --- | --- | --- |
| Index and discovery | Index declared project/approved dependency lanes; return bounded results with freshness, incompleteness, and failure semantics. | Business-source editing, arbitrary cross-project discovery, or machine-wide source scanning. |
| Project installation and removal | Create, validate, deactivate, and remove only the managed project integration under its ownership and preservation rules. | Implicit UPM Package removal, machine dependency uninstall, or unrelated configuration deletion. |
| Runtime operation | Schedule queries and maintenance; manage attributable project-owned backend execution and bounded startup/shutdown behavior. | Machine-wide process governance, external MCP-client control, or Windows restart. |
| Prerequisites | Check the reviewed dependency contract and, with its required authorization, delegate to the reviewed installer. | Treat project removal as shared-dependency removal or silently take over machine configuration. |
| CodeDB commands | Attribute execution, prevent conflicting operation ownership, preserve real results, and provide bounded progress and explicit exception/unknown states. | Guaranteed automatic recovery from every crash, unlimited retries, or synthetic terminal receipts. |
| CodeDB history | Retain known facts and unknown outcomes; address effects relevant to the current project and proposed change. | Reconstruct every old execution or establish an all-history/all-process census as a normal user prerequisite. |
| Unity experience | Enqueue intent asynchronously, render cached observations, and avoid blocking Play, reload, repaint, or normal exit. | Heavy filesystem, hash, process, lock, or synchronous IPC work in main-thread UI callbacks. |

Read-only discovery means business source is not edited. Index creation,
registration, runtime ownership publication, and command journals have their
declared generated-state effects. A Probe or lease publication that writes
state is not relabelled as effect-free observation.

## Component Responsibility Matrix

These are logical responsibilities mapped to the existing components, not a
requirement for additional services, scripts, or persistence layers.

| Component or role | Owns | Does not own |
| --- | --- | --- |
| Unity Bridge / Manager | Unity signals, captured project/Package context, intent, confirmation, UI lifetime, and cached presentation. | Backend resource mutation, synchronous maintenance, or authorization inferred from visible UI state. |
| Per-operation execution owner | Execution and authoritative command evidence for its assigned action. Direct commands use the one-shot writer; Supervisor requests use Supervisor authority. | Borrowing the other route's result, silently changing route, or declaring Ready from an exit code. |
| Worker / process runner | Bounded dispatch, process-result collection, cancellation/timeout observations, and delivery of data to the caller. | Fabricating a terminal receipt, assuming rollback after timeout, or calling Unity UI APIs from the worker. |
| Project-integration backend | Resource-level checks and serialized changes to managed registration, project control, selection, activation, removal, and cleanup under the existing materializer/instance contracts. | Unknown-owned resources, arbitrary deletion, or a second weaker removal engine. |
| Supervisor | Project-level query/maintenance scheduling and Coordinator admission and operation management. | Machine-global authority or independent guessing about lower-level process ownership. |
| Coordinator | Lifecycle and ownership of its Provider and adapter execution. | Project install/uninstall policy or external client lifecycle. |
| Provider / adapters | Language analysis, indexing, and search under their reviewed contracts and declared lanes. | Unity UI, project MCP registration, or integration-removal decisions. |
| MCP wrapper | Selected-instance routing, query policy, bounded merging/output, and its declared connection/lease behavior. | Independent generation policy, project reinstall, or client configuration reload. |
| Status aggregation | Current product-state composition through the existing StatusSnapshot / ProductStatusBuilder path using attributable facts. | Old-command result publication or new-mutation authorization. |
| Package identity contract | Authoritative runtime-version, generation, and closure declarations in `Payload~/payload-manifest.json`. | Independently maintained version/generation constants in callers. |

The resource owner is authoritative within its declared resource domain, not
over every downstream resource. Manager intent admission is not backend
mutation admission. A backend safety check at the point of effect is not a
second UI decision. Helpers may implement an owner's operation but may not
publish competing decisions under another authority.

For each action, freeze its execution route and resource-owner entry points
before implementation. One action has one command-result publisher. The
logical backend row does not grant every materializer/engine helper authority
over every control or registration file; the implementation packet must name
the existing writer for each touched resource. A responsibility gap is exposed
as a design decision, not concealed by naming two co-equal owners.

Runtime process authority remains hierarchical:
Bridge contacts Supervisor; Supervisor owns Coordinator admission; Coordinator
owns Provider/adapter children. This does not authorize stopping them in this
documentation checkpoint. Existing owned-process shutdown and external-holder
preservation rules remain intact.

## Data And External Boundaries

- Business source, user-authored files, and unrelated configuration remain
  user-owned. Modify only the declared CodeDB-managed configuration fields,
  preserving unrelated values and recoverable content as required.
- Indexes, Host/runtime files, caches, and logs use existing project-scoped,
  ignored runtime boundaries. Existing Manager-action evidence uses its
  validated user-local, project-bound boundary; this is not a migration to a
  new storage root.
- Machine Provider/Node installations are shared prerequisites, not project
  uninstall targets. Reviewed dependency installation is a separately declared
  effect, not blanket machine-administration authority.
- UPM resolves/removes the Package; project-integration removal is a separate
  CodeDB action. Removing the Package alone does not certify project uninstall.
- Codex or another MCP client owns its session and configuration-reload timing.
  Correct registration and server handshake do not prove that an already-open
  client task has loaded the new tools. No forced client stop or session rebind.
- Immutable artifacts/generations and original evidence remain preserved.
  Retained lease-bound content is not active authority and is not permission
  for recursive deletion. Logical uninstall and physical cleanup remain distinct.

## Outcome And Recovery Rules

1. Judge command outcome, current product state, and new-change admission
   independently. Never substitute one for another.
2. Preserve CodeDB's own effects and records honestly. Unknown history does not
   force current status to be non-Ready or prohibit independent read-only
   discovery, but it also does not waive a relevant write conflict or missing
   mutation-safety evidence.
3. Recovery addresses the requested action's relevant project state and owned
   execution only. It does not require reconstructing the old command outcome
   before allowing independent current-state observation.
4. No Windows reboot, boot-checkpoint scheme, global process census, global
   PowerShell/Node shutdown, or new machine-administration permission is a
   CodeDB recovery prerequisite or fallback in this scope.
5. New ownership records cannot retroactively fill absent old evidence. A new
   lock/epoch does not establish safety against an old executor that does not
   obey it. Do not claim a passing recovery branch without the required proof.
6. Logical uninstall, authenticated `Uninstalled`, retained-content cleanup,
   and fresh Install keep their existing meanings. A verified inert retained
   closure need not be fully deleted before fresh Install; ambiguous active
   authority still refuses mutation.
7. Bounded failure/unknown presentation and a specific explanation are valid
   outcomes. UI timeout or cancellation is not proof that backend effects
   stopped. Do not shift an unresolved proof gap into repeated user restarts,
   manual state deletion, or another system-level prerequisite.
