# v0.3.0 P0: Control Contract Migration And Explicit Reinstall

Status: planned; the product decision is approved, implementation has not
started.

Date frozen: 2026-08-27.

This task is a companion to the [P0 Supervisor runtime ownership and crash
recovery task](v0.3.0-p0-supervisor-runtime-recovery.md). It addresses the
boundary between a new control contract and runtime evidence left by an older
development or package version.

## Why This Task Exists

The current development snapshot can leave a Supervisor state from an older
schema and selected instance while `current-instance.json` already points at a
new instance. The new owner validator correctly refuses the old state because
its process identity and contract evidence cannot be authenticated, but the
old state also occupies the same fixed control path as the new Supervisor.

This creates a fail-closed dead end:

```text
old Supervisor state remains
    -> current instance changes
    -> new validator rejects the old state
    -> stale takeover cannot run
    -> new Supervisor cannot use the shared control path
    -> Manager reports Needs attention
```

The defect is not specific to one generation identifier. It is a control-plane
migration problem caused by independently persisted selection and owner state,
an unversioned control namespace, and no atomic activation handoff. Requiring
every historical development snapshot to migrate transparently would create an
unbounded compatibility matrix and would encourage unsafe exceptions to the
owner validator.

## Frozen Product Decision

Major control-plane changes do not require forced compatibility with every old
development snapshot. A trusted project detects an incompatible control
contract read-only and exposes one explicit `Reinstall CodeDB` action. The
action rebuilds the project-local runtime through the new candidate and atomic
activation path. It is not a request to manually delete state, clear leases,
close Codex sessions, or reinstall the UPM package.

The support policy is:

| Situation | Product behavior |
| --- | --- |
| Same control contract and compatible payload/generation update | Automatic side-by-side convergence |
| Incompatible control schema, Supervisor protocol, or control layout | `Needs attention` with `REINSTALL_REQUIRED` and one `Reinstall CodeDB` action |
| Missing or invalid Node/Provider prerequisite | `Missing prerequisite`; zero project mutation |
| User intentionally removes project integration | Confirmed `Uninstall CodeDB from Project` |
| Unknown or ambiguous evidence | Fail closed; never delete or stop it; a disjoint new namespace may still be prepared |

Published `v0.2.x` artifacts and unpublished intermediate `v0.3` snapshots do
not receive an individually maintained migration path. A v0.3 release must
declare the control contract it supports and the explicit reinstall boundary.

## Goals

1. Separate Package payload identity, project activation identity, and
   Supervisor process ownership identity.
2. Give each control contract an isolated namespace so incompatible old
   evidence cannot block a new verified instance.
3. Make candidate activation and Supervisor handoff recoverable from one
   durable transaction/epoch.
4. Preserve external MCP clients, user configuration, immutable instances,
   leases, and last-known-good state.
5. Make the ordinary user action explicit, bounded, observable, and idempotent.
6. Keep Unity as an asynchronous Bridge and cached Manager client.

## Contract Model

The three identities below must remain distinct:

### Package payload contract

`Payload~/payload-manifest.json` remains authoritative for the immutable
generation, payload closure, bootstrap protocol, and declared generation
transitions. A `poc.*` identifier is not a Supervisor control version.

### Project activation contract

The project control record identifies the selected instance, activation epoch,
runtime contract hash, and last-known-good selection. It is the only writable
project selection authority. A candidate is not current until its complete
closure and usability evidence have been verified.

### Supervisor ownership contract

Supervisor state and lock evidence identify the control contract, project,
selected instance, owner epoch, PID/start identity, exact executable/argv,
authenticated pipe, and publication phase. The state is accepted only when
all values belong to the same activation epoch.

The Bridge, PowerShell, Node, wrapper, and Manager consume these records. They
may validate the contract, but they must not maintain separate current-
generation or migration policy.

## Versioned Control Namespace

The fixed shared path `control/supervisor` must not be the identity boundary
for incompatible contracts. The implementation must introduce a reviewed
versioned or contract-keyed namespace for at least:

- Supervisor state and lock;
- operation journal and result evidence;
- authenticated pipe identity;
- Supervisor and coordinator logs;
- takeover claims and retirement markers.

The exact directory spelling can be selected during implementation, but the
following invariants are mandatory:

1. A new contract resolves its own namespace from the trusted Package
   contract, not from an untrusted old state file.
2. An old incompatible state is retained or isolated, never silently deleted.
3. A stale or malformed old state cannot authorize a process or block a
   disjoint new candidate.
4. Stable wrapper resolution follows the atomically selected instance and
   contract record, not a hard-coded `poc` or legacy path.
5. All paths remain project-local, no-reparse, and outside global Codex
   configuration.

## Compatibility Classification

Classification happens before validating an old state against the new context:

- `CURRENT`: same supported control contract and authenticated owner/selection;
- `COMPATIBLE_STALE`: supported contract, complete evidence, owner proved gone;
- `OBSOLETE_REINSTALL_REQUIRED`: known older contract, no supported transparent
  migration, no live owner action authorized;
- `INVALID_OR_AMBIGUOUS`: malformed, redirected, conflicting, or unauthenticated
  evidence;
- `MISSING`: no evidence for the current contract.

`OBSOLETE_REINSTALL_REQUIRED` is a user-facing recoverable condition. It must
not be conflated with a live process mismatch, and it must not authorize a
blind cleanup of the old state. `INVALID_OR_AMBIGUOUS` remains fail-closed;
the new contract proceeds only through a disjoint namespace and a verified
activation path.

## Reinstall State Machine

The explicit action uses one serialized project operation:

```text
READ_ONLY_PREFLIGHT
    -> PROVISION_CANDIDATE
    -> VERIFY_CANDIDATE
    -> ACTIVATE_EPOCH
    -> PUBLISH_READY
    -> RETIRE_OLD_INSTANCE
```

Any failure before activation leaves the current and last-known-good selections
unchanged. A failure after a partial activation is recovered from the journal
to either the committed new epoch or the prior last-known-good epoch. Retired
cleanup is asynchronous and never gates the new instance's usability.

The candidate verification must include the existing package-owned checks:

- immutable Host and instance closure;
- machine prerequisite and Provider contract;
- MCP initialize and exact read-only tools/list;
- usable `codedb_status`;
- one bounded `codedb_text_search`;
- project identity, path, reparse, and ownership boundaries.

## Handoff And Recovery

Activation publishes one durable record containing at least:

- control contract id/version and hash;
- candidate and selected instance ids;
- selected generation id;
- activation epoch and operation id;
- current/last-known-good disposition;
- publication phase and timestamp.

Supervisor startup reads that record first. It reuses an authenticated owner,
reattaches an exact live child, or takes over only a proved-stale compatible
owner. It never treats an old PID, timestamp, or parseable JSON as ownership.

If an external MCP client still holds the previous immutable instance, the
client remains alive and pinned to that instance. The new instance serves new
connections. Old leases and package-owned retired content are cleaned only
after natural drain and exact ownership verification.

## Bridge, Lifecycle, And Manager Boundaries

- Unity callbacks enqueue lifecycle intent and consume cached results only.
- Supervisor and its workers perform filesystem, process, hash, lock, and
  journal work off the Unity main thread.
- Domain Reload and Play transitions reconnect to the same healthy contract;
  they do not start a second owner.
- Opening or repainting Manager never starts a migration or a Supervisor.
- Manager presents `Needs attention` plus `Reinstall CodeDB` for the explicit
  migration condition; technical schema, PID, epoch, and path details remain
  diagnostics.
- `Missing prerequisite` takes precedence over Reinstall and causes no project
  mutation or retry loop.

## Safety Invariants

The migration must preserve all existing boundaries:

- external MCP, Codex, Unity, and unrelated processes are never stopped;
- only independently authenticated Package-owned watcher/coordinator children
  may be stopped during retirement;
- unrelated TOML keys, tables, comments, order, BOM/EOL, and global config are
  preserved;
- immutable generations are never rewritten in place;
- reparse, path, ownership, lease, transaction, rollback, and prerequisite
  checks remain fail-closed;
- cancellation, crash, retry, and repeated Reinstall are idempotent.

## Scope And Non-Goals

This task includes the control contract, namespace, compatibility classifier,
activation journal/epoch, Reinstall route, and the minimal Bridge/Manager
changes needed to consume them.

It does not rewrite the Provider, query protocol, immutable payload contents,
MCP TOML merge rules, or the full Discover Read feature. General query-first
scheduling, complete Domain Reload instrumentation, and broad Supervisor
features remain separate v0.3 slices, but they must consume this contract
instead of adding another state authority.

It does not add user-global MCP registration, a machine-global daemon, or a
manual cleanup requirement. It does not backport lifecycle fixes to `v0.2.x`.

## Focused Acceptance

1. A clean project performs first installation without Manager intervention.
2. A same-contract generation update converges automatically and preserves an
   active old MCP lease.
3. A schema/protocol/layout-incompatible old state is classified as
   `REINSTALL_REQUIRED` without deleting or stopping anything.
4. One confirmed Reinstall provisions a fresh namespace and instance, verifies
   usability before activation, and reaches `Ready` without a second action.
5. The current dirty-development symptom (new current selection plus old
   schema state) no longer blocks the new contract after explicit Reinstall.
6. Candidate failure before activation, crash at each activation phase,
   rollback, retry, and repeated Reinstall are deterministic and idempotent.
7. Active external MCP remains alive and byte-pinned; old leases drain before
   cleanup; unrelated project/user configuration remains byte-identical.
8. Manager reopen, tab changes, Play, and Domain Reload do not duplicate
   Supervisor or materializer processes.
9. Missing/invalid/hash-mismatched prerequisites return `Missing prerequisite`
   with zero project mutation.
10. Source audit finds no independent current-generation or control-path policy
    in C#, PowerShell, Node, wrapper, and Manager code.

## Validation Order

Per implementation slice, run only L0 syntax/compile and the affected focused
tests. At code freeze, run once:

1. control-contract and migration harnesses;
2. candidate/activation/rollback and external-process safety tests;
3. PowerShell/Node/JSON/package boundary and hash-closure checks;
4. affected Unity EditMode tests, then one fresh full EditMode pass;
5. one fresh local cold-start/Play/Domain Reload pass;
6. real new-Codex-task and third-party Package-only gates in their declared
   environments.

Real Codex Desktop tool injection, released artifacts, and third-party
Package-only acceptance remain `DEFERRED` until actually executed. No direct
wrapper probe or old test result substitutes for those gates.

## Delivery Order

1. Freeze the control contract schema and namespace derivation.
2. Add read-only compatibility classification and the `REINSTALL_REQUIRED`
   result mapping.
3. Implement activation journal/epoch and fresh namespace provisioning.
4. Route candidate verification, atomic activation, rollback, and retirement
   through one serialized operation.
5. Migrate Bridge, Lifecycle, stable wrapper, and Manager to the new contract.
6. Add old-schema, interrupted-handoff, active-MCP, and clean-install fixtures.
7. Run the focused and final layered gates; only then consider the current
   control plane a v0.3 release boundary.

## Definition Of Done

The task is complete when an incompatible old control contract is an explicit,
safe, one-action Reinstall condition; a fresh verified instance can be
activated without touching or stopping unrelated old state; crash/retry and
external MCP behavior remain safe; and fresh Unity evidence confirms the
control-plane transition does not block the Unity main thread.
