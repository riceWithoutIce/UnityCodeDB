# UnityCodeDB v0.2.5 Upgrade Closure Roadmap

Status: `v0.2.5-preview.3` was published from commit `d3d9652` with immutable
Host generation `poc.30`. Its complete materializer regression, package
boundary and payload hash closure, PowerShell and Node syntax, JSON parsing,
diff checks, Unity 2022.3.20f1 EditMode `200/200`, and local Manager UI
acceptance passed on 2026-08-13. Third-party Package-only acceptance then found
a release blocker: `Repair CodeDB` rejects a standards-compliant target MCP
server that contains a legal child table such as
`[mcp_servers.<project-slug>.tools.<tool-name>]`. The failure is fail-closed and
made no Host or MCP configuration write, but the normal recovery path is not
usable for this valid configuration. Third-party acceptance is therefore
`PAUSED`, not passed. The published preview.3 tag remains immutable; the narrow
fix targets `v0.2.5-preview.4`, and stable `v0.2.5` is not yet approved.

## Product Decision

After Unity successfully resolves and loads the Package, CodeDB must behave the
same regardless of how the Package arrived or whether the Unity project uses
Git, SVN, Perforce, another version-control system, or none. Package runtime
logic must not detect, invoke, or branch on a version-control system or Package
installation source. It must reconcile every package-owned project state that
can be changed safely without requiring the Manager window, Sync, process
termination, PID cleanup, lease cleanup, authorization JSON, or deletion of
unrelated runtime data.

Automatic repair remains fail-closed for real CodeDB-owned file drift, unowned
path collisions, invalid manifests, path escapes, unsupported bootstrap
transitions, and downgrades. Safety derives only from the canonical project
root, Package manifest and allowlist, CodeDB ownership marker, byte hashes,
project lock, durable transaction and rollback, reparse-point checks, generation
leases, and explicit confirmation where required. Manual Start, Stop, Restart,
automatic-start policy, and automatic-update policy remain independent.

## Confirmed Preview.3 MCP Registration Defect

The third-party project contains this legal TOML shape:

```toml
[mcp_servers.codedb-balance]
command = "node"
args = ["AIWork/codedb/wrapper/codedb-balance-wrapper.mjs", "--root", "."]
startup_timeout_sec = 120

[mcp_servers.codedb-balance.tools.codedb_text_search]
approval_mode = "approve"
```

A standards-compliant TOML parser accepts it, but preview.3 reports
`ambiguous dotted-key collision for mcp_servers.codedb-balance`. The current
MCP merge preflight mistakes a legal descendant table for a collision with the
target server table, and the materializer regression suite encodes that wrong
expectation.

The ownership boundary is narrower than the current parser assumes. CodeDB
owns only these direct keys in the target server table:

- `command`
- `cwd`
- `args`
- `startup_timeout_sec`

Other direct keys and descendant tables, including `tools.*`, are user- or
client-owned and must remain byte-preserved unless they create a real TOML
namespace conflict with one of the four managed keys. A target scalar, target
array table, duplicate target declaration, or a managed key declared as a
table remains an unsafe conflict and must fail closed.

## Delivery Route After Preview.3

### Phase A: v0.2.5-preview.4 Release Blocker

1. Correct MCP target-table discovery so a legal target child table is not
   treated as a collision. Cover parent-first, child-first, and child-only
   declaration order.
2. Rewrite only the four CodeDB-managed direct keys. Preserve target custom
   keys, descendant tables, unrelated servers and tables, comments, ordering,
   BOM, and line-ending style.
3. Continue rejecting invalid TOML, duplicate or incompatible target
   declarations, target scalars and array tables, and namespace collisions
   involving a managed key with byte-exact zero writes.
4. Retain atomic publication, replacement-time pre-image backup, rollback,
   idempotency, and unrelated-byte invariants.
5. Add a sanitized fixture matching the third-party configuration and correct
   the regression that currently expects its rejection.
6. Run focused MCP merge tests, complete materializer regression, package
   boundary/hash closure, syntax checks, Unity EditMode, and one real Repair in
   the local Unity validation project before publishing preview.4.
7. Resume third-party Package-only acceptance only with preview.4. Do not count
   preview.3's failed attempt or local automation as third-party acceptance.

Phase A is a compatibility fix, not authorization for a broad TOML parser
rewrite or materializer decomposition.

### Phase B: Stable v0.2.5 Closure

1. Carry a second-level confirmation credential explicitly from Manager to
   Actions, materializer invocation, and the Package-owned mutation entry
   point. No lower layer may manufacture confirmation by hard-coding `true`.
2. Classify historical MCP and watcher ownership before any repair mutation.
   An active legacy, unknown, invalid, path-escaped, reparse-point, or
   mutation-intersecting owner blocks all writes. A valid non-intersecting
   immutable-generation lease is retained and permits repair to continue.
3. After process ownership is proven safe, evaluate Host and MCP configuration
   phases independently. Unsafe Host state yields `BLOCKED`; safe Host plus
   unsafe MCP configuration may converge Host only and yield
   `PARTIALLY_REPAIRED`; two safe phases yield `REPAIRED`.
4. Return one structured command result with `outcome`, `phase`, `reason_code`,
   `mutated_scopes`, and `next_action`. Reduce it through one state reducer so
   the Manager does not infer a second, contradictory status.
5. Establish shared golden vectors for the C#, PowerShell, and Node project
   slug/identity algorithms.
6. Generate Package, payload, generation, pointer, Editor identity, and hash
   closure inputs from one reviewed release descriptor so release identities
   cannot drift independently.
7. Re-run the stable release gates and complete third-party Package-only
   acceptance. Deferred two-project isolation and elevation matrices remain
   explicit and are never converted to `PASS`.

### Phase C: Post-v0.2.5 Progressive Refactoring

1. Split the materializer by semantic ownership: Identity/Manifest,
   Path/Ownership, Lease/Process, Transaction/Recovery, MCP Config, and Action
   Orchestration.
2. Split Editor lifecycle behavior into a scheduler, a pure decision model,
   and an effect executor.
3. Extract Manager presentation and action policy into a testable ViewModel.
4. Preserve the stable external contracts and migrate incrementally with
   characterization tests; do not combine this refactor with preview.4.

## Confirmed Preview.2 Defect

The tracked ownership marker can arrive through Git claiming the current
package generation is installed while `AIWork/.runtime/` remains absent or on
an older generation because that directory is intentionally ignored. The
preview.2 materializer treats the resulting missing and older runtime files as
`ManagedMissing` or `ManagedDrift`, converts them to `CONFLICT`, and refuses the
safe package reconstruction.

The Editor then requires `current.json` to match the current Package identity,
classifies an otherwise valid previous generation as `Invalid`, redirects Host
paths under `host/unavailable`, and still exposes actions that attempt to run
scripts there. Persisted `upgrade-state.json` can simultaneously report a stale
older generation as green `CURRENT`.

Preview.2 also calls `git rev-parse` while planning a DryRun. In Windows
PowerShell 5.1, the expected native failure for a non-Git project is promoted to
a terminating error by the script's global stop policy before the optional Git
result can be handled. Strict first-adoption Sync and Remove additionally bind
authorization to a Git worktree, HEAD, index, and ignored authorization file.
That makes version control an accidental product prerequisite. Preview.3 must
remove the prerequisite and all version-control command execution from Package
runtime behavior; merely suppressing the DryRun error is insufficient.

## Retained Preview.2 Scope

The controlled legacy Redeploy path introduced in preview.1 and completed in
preview.2 remains part of v0.2.5. Published byte-exact `poc.9`, `poc.16`, and
`poc.20` flat Hosts must still receive focused active-owner guidance, allow the
Manager to stop only a recognized legacy watcher, refuse to terminate external
MCP clients, publish the current generation transactionally, and regenerate
only the reviewed ignored runtime config. Preview.3 must retain this coverage
while advancing the target generation from `poc.29` to `poc.30`.

## Preview.3 Required Scope

### Portable Adoption And Runtime State

1. Introduce a portable CodeDB ownership-marker contract that records project
   adoption, requested package/payload identity, and only package-owned stable
   Host-file ownership. Its trust does not depend on how the project was copied,
   archived, installed, or versioned.
2. Stop using the portable marker as proof that local generation files or
   `current.json` exist on the current machine.
3. Derive actual runtime installation state from the selected pointer,
   generation manifest, package-managed generation closure, leases, and
   materializer diagnostics under ignored runtime.
4. Read existing schema-1 markers compatibly. Runtime entries in a schema-1
   marker may establish historical package intent but cannot turn ordinary
   local-runtime absence or a valid older pointer into user drift.
5. Permit first adoption to converge automatically when every CodeDB-managed
   target is absent and all project, manifest, path, and configuration preflight
   checks succeed. If safe automatic convergence is not possible, offer the
   single confirmed `Repair CodeDB` workflow. Neither path may require
   version-control metadata, commands, tools, or authorization JSON.

### Automatic Runtime Reconstruction

After Package resolution or script reload, automatically reconcile these
project states:

- a fresh project has no marker and every CodeDB-managed target is absent;
- portable Host and marker are current while local runtime is absent;
- portable Host and marker are current while a valid older generation remains;
- a known lower portable marker and matching lower generation both remain;
- the current package generation already exists byte-exact but the marker or
  pointer publication is incomplete;
- a recoverable automatic-upgrade transaction was interrupted.

The automatic path must acquire the project-local materializer lock, re-check
ownership, stage on the same volume, validate the complete manifest and hashes,
publish the immutable generation, retain a validated last-known-good pointer,
switch `current.json` atomically, and complete watcher handoff. Existing MCP
requests stay pinned to their leased generation and are never terminated.

Do not auto-repair a partially present candidate generation with unexpected
bytes, an invalid previous pointer, unmanifested generation content,
CodeDB-owned Host drift, or a path/identity collision. Report the exact boundary
instead with byte-exact zero writes outside recoverable transaction evidence.

### Version-Control And Installation-Source Independence

1. Package runtime and Editor code must not execute or probe `git`, `svn`,
   Perforce, or another version-control command. It must not inspect worktrees,
   repositories, HEAD/revisions, indexes, staging, ignore rules, or installation
   URLs to authorize or classify a CodeDB action.
2. DryRun, Setup, automatic Upgrade, `Repair CodeDB`, Verify, advanced Sync,
   and Remove must use the same CodeDB-owned state machine in projects with or
   without version-control metadata and when version-control executables are
   absent from `PATH`.
3. Remove the tracked-host authorization JSON contract from the supported
   product workflow. Confirmation authorizes only the exact manifest-closed
   CodeDB scope; it never authorizes overwriting unknown or drifted content.
4. Resolve Package payloads from Unity's loaded Package location without
   assuming a fixed source layout or writable Package directory. Never mutate
   Package source content.
5. Treat unknown same-name files, malformed ownership evidence, drift, path
   escapes, reparse points, active unsafe owners, and ambiguous MCP configuration
   as CodeDB safety conflicts. Refuse with focused guidance and zero unrelated
   writes; do not ask the user to initialize or change version control.
6. Keep all user-facing status and recovery guidance free of Git, SVN, staged,
   HEAD, checkout, and authorization-file prerequisites.

### Generation And Status Truth

1. Validate pointer and generation integrity independently from whether their
   Package version is the currently loaded Package.
2. Represent a complete compatible lower generation as `PREVIOUS` or
   `UPGRADE_PENDING`, not `Invalid`.
3. Reserve `Invalid` for malformed identity, unsupported protocol, path escape,
   missing closure, hash drift, or unmanifested generation content.
4. Correlate persisted upgrade state with the loaded target generation. An
   older `CURRENT`, `CHECK_FAILED`, or transient phase is historical/stale and
   cannot be rendered as the current update result.
5. Validate last-known-good semantics before reporting it as retained.

### Manager And Command Safety

1. Centralize the readiness gate for every command that resolves a Host script.
2. Never construct or execute `host/unavailable/scripts/...`.
3. Disable Prepare, Regenerate, Verify, Provider Guidance, index, watcher, and
   registration actions while their required generation is unavailable.
4. Present `UPGRADE_PENDING`, `REBUILD_REQUIRED`, `INSTALLING`, `SWITCHING`,
   `DRAINING`, `CURRENT`, `ROLLBACK`, `CHECK_FAILED`, `CONFLICT`, and
   `DOWNGRADE_REVIEW_REQUIRED` without contradictory green rows.
5. Retain one manual `Update now` or `Retry update` fallback when automatic
   mutation is disabled or a deterministic failure requires review.

### One-Click User Recovery

The Manager must expose one user-facing `Repair CodeDB` action as the final
recovery path. It replaces the current expectation that a user selects a
tracked-host authorization file, runs separate Host actions, copies a TOML
snippet, or manually reconstructs package/runtime state. Existing Inspect,
Verify, Sync, Remove, Redeploy, registration-draft, and validation actions may
remain under advanced diagnostics, but they are not the product recovery path.

1. Keep `Repair CodeDB` available when the selected Host is missing, previous,
   unavailable, conflicted, or left in an interrupted upgrade state. Invoke the
   Package-owned recovery entry point; never resolve the action through
   `host/unavailable` or another unvalidated installed generation.
2. One click opens a second-level confirmation dialog. The dialog must state
   the exact project-local scope that may be repaired or quarantined, the data
   that will be preserved, that unrelated MCP configuration will not change,
   and that an already running MCP client may require a new session. `Cancel`
   performs zero writes; the primary confirmation is `Repair CodeDB`.
3. After confirmation, run one orchestrated workflow: acquire the materializer
   lock, recover or quarantine deterministic CodeDB-owned ignored Host residue,
   reconstruct and validate the current immutable generation, repair current
   and rollback pointers, migrate only a byte-exact generated runtime config,
   repair the project-level MCP registration, verify the resulting setup, and
   restore the user's existing automatic-start and automatic-update policies.
   A project with no ownership marker is eligible when the entire managed scope
   is absent; unknown or conflicting content blocks with zero writes.
4. The scoped cleanup may mutate only reviewed package-owned paths under
   `AIWork/.runtime/codedb/host/` and materializer transaction state. Prefer a
   recoverable quarantine before deletion. Never remove Provider binaries,
   indexes, adapters, customized runtime configuration, unrelated generations,
   business files, version-control metadata, or files outside the CodeDB
   ownership scope through this recovery action.
5. Never terminate an external MCP client. Classify each live MCP lease against
   its Package-owned immutable-generation closure and retain that process,
   lease, and generation whenever the planned recovery paths do not intersect
   the closure. Re-read leases before pending rollback, quarantine, generation
   publication, and transactional Host publication; an intersecting mutation,
   unknown owner, path escape, reparse point, managed-file drift, or ambiguous
   ownership blocks before that write. A safely retained historical MCP
   generation is a successful `REPAIRED` outcome, not a request to wait for
   drain or click Repair again.
6. Create or repair only `[mcp_servers.<project-slug>]` in the trusted project
   `.codex/config.toml`, using the reviewed relative wrapper, `cwd = "."`,
   `--root "."`, and bounded startup timeout. Preserve all unrelated tables,
   keys, comments, ordering, and line-ending style. Publish atomically with a
   recoverable backup. Invalid TOML, duplicate target tables, or an ambiguous
   conflicting target table must not be overwritten silently.
7. Finish with one result: `REPAIRED`, `PARTIALLY_REPAIRED`, or `BLOCKED`, with
   completed phases and the single next user action. A successful registration
   states that new Codex sessions use the repaired project config; it must not
   claim that an already running client hot-reloaded it.

### Downgrade And Package Selection Changes

1. Never downgrade automatically.
2. Detect a valid runtime generation newer than the Package currently loaded by
   Unity instead of misclassifying it as user drift. The result cannot depend on
   how that Package version was selected.
3. Offer a confirmed, project-scoped rebuild/switch to the selected Package
   only after active MCP and watcher owners have drained.
4. Preserve Provider binaries, indexes, adapters, runtime configuration,
   policies, registration, unrelated generations, and unrelated project files.
5. Keep a valid rollback pointer and never let an older Package delete an
   unvalidated newer generation through a broad cleanup path.

### Metadata-Only Package Updates

1. Treat Package version metadata separately from Host compatibility identity.
2. When payload sequence, generation, bootstrap protocol, manifest closure, and
   hashes are identical, a Package-only version change must not invalidate the
   selected generation or require a fabricated Host migration.
3. Reusing one payload sequence with different identity or bytes remains a
   sequence collision and must fail closed.
4. Add a release gate that verifies Package, payload, generation, pointer,
   Editor constants, changelog, and tag identities before publishing.
5. Preview.3 still advances to `poc.30` because its materializer and Host
   contract change; metadata-only support applies to future releases.

### Runtime Configuration Migration

1. Automatically replace a runtime config only when it is byte-exact to a known
   previously generated template and the new template is compatible with the
   retained project/provider identity.
2. Never silently overwrite a customized runtime config.
3. Customized incompatible configuration reports one focused reviewed action;
   it does not block package-owned Host reconstruction when the old backend can
   remain safely retained.
4. Preview.3 must leave existing config, Provider binaries, indexes, adapters,
   MCP registration, manual runtime state, and update/start policies byte-exact
   when no config-schema migration is required.

### Retry And Recovery Policy

1. Retry project-lock contention, a concurrently running upgrade, and bounded
   transient Windows sharing races with capped backoff.
2. Do not permanently suppress automatic reconciliation for failures that made
   no unsafe mutation and are classified as transient.
3. Suppress repeated automatic mutation for deterministic validation failure,
   watcher handoff rollback, incomplete rollback, drift, or collision; expose
   the persisted reason and manual retry.
4. Recover durable automatic-upgrade journals before starting another mutation.

## Upgrade Acceptance Matrix

Automated materializer and Unity EditMode coverage must include:

1. direct and skipped upgrades from published `poc.22` through `poc.29`;
2. schema-1 marker plus no local Host runtime, matching a portable project copy;
3. current portable marker plus valid older runtime on another machine;
4. old marker plus old runtime, current marker plus no pointer, and a byte-exact
   pre-published candidate generation;
5. partial, drifted, unmanifested, path-escaped, and hash-colliding runtime;
6. metadata-only Package update and same-sequence different-payload rejection;
7. explicit downgrade with stopped owners and rejection with live owners;
8. default-on, explicit-off, and invalid automatic-update policies;
9. byte-exact generated config migration and customized-config preservation;
10. concurrent same-project Editors, old-generation MCP/watcher leases, bounded
    transient retry, injected crash, rollback, and recovery;
11. stale upgrade-state and invalid last-known-good presentation;
12. every Host-dependent Manager action while generation state is unavailable,
    previous, installing, failed, and current.
13. supported flat legacy Redeploy with no owners, a recognized watcher, an
    external MCP blocker, drift, and rollback.
14. `Repair CodeDB` availability for missing, previous, unavailable, conflict,
    interrupted, and current Host states without resolving an installed Host
    script before Package-owned preflight succeeds;
15. confirmation cancellation with byte-exact zero writes, plus one confirmed
    recovery that needs no authorization JSON, copied snippet, or second action;
16. scoped quarantine and reconstruction for stale pointer, journal, candidate,
    and ignored-runtime residue, including non-conflicting current/previous MCP
    lease retention, pending-rollback intersection refusal before writes,
    custom-config preservation, unrelated-generation preservation, and an
    injected partial-phase failure;
17. MCP registration with a missing config, an unrelated multi-server config,
    a current target section, a stale target section, and legal target child
    tables in parent-first, child-first, and child-only order. Preserve custom
    direct keys and child tables byte-exact. Refuse without writes for invalid
    TOML, duplicate or incompatible target declarations, path escape, and real
    managed-key namespace collisions. Repeated repair must be idempotent.
18. equivalent DryRun, first adoption, Upgrade, Repair, Verify, Sync, and Remove
    outcomes in a project with no version-control metadata, a project containing
    Git metadata, and a project containing SVN metadata;
19. a `PATH` with no version-control executables plus instrumented `git`, `svn`,
    and `p4` sentinels that prove Package runtime invokes none of them;
20. Package payload resolution from representative cached, local, and embedded
    layouts with a read-only Package source, including proof that no Package
    source byte is changed;
21. fresh empty-scope automatic adoption, confirmed first-adoption Repair,
    repeated idempotent Repair, unknown same-name conflict with zero writes, and
    ownership-bounded Remove without authorization JSON.

Package boundary, payload hash closure, Node syntax, PowerShell syntax, JSON,
Unity EditMode, fixture/source equality, Package-source immutability, repository
diff checks, and clean release-tree checks remain mandatory.

## Preview.4 Third-Party Acceptance

Starting from the preview.3 third-party failure state, update only the Package
to `v0.2.5-preview.4`. Without opening the Manager or clicking Sync/Update,
Unity compilation and Domain Reload must converge to:

```text
Host payload = CURRENT
Host generation = poc.30
Host upgrade = CURRENT / poc.30
```

Repeat from a fresh project copy with portable adoption state and no local
runtime, then from a blank Unity project with no version-control metadata or
version-control executable available. Confirm that empty-scope first adoption
converges, actual CodeDB-owned drift still blocks without writes, and manual
automatic-update disablement prevents automatic mutation while preserving an
enabled `Update now` fallback. Repeat one successful Package load from a
different Unity-supported source layout and confirm identical CodeDB behavior.

Also reproduce one supported broken local state in which automatic recovery did
not converge. Open the Manager, click `Repair CodeDB` once, review and accept
the second-level confirmation, and perform no other CodeDB action. The workflow
must converge the Host and project MCP registration or report one exact unsafe
boundary. Confirm that it requested no authorization file or manual TOML edit,
preserved unrelated project/MCP content, and that a new Codex session can query
the repaired project registration.

The third-party project must retain the legal
`[mcp_servers.<project-slug>.tools.<tool-name>]` table that exposed the
preview.3 defect. After Repair, verify that the four managed parent keys are
current while the tool table, its keys, comments, and unrelated configuration
remain unchanged. The preview.3 attempt is recorded as a failed acceptance
observation and is never promoted to `PASS`.

## Release-Line Hygiene

1. Keep the published `v0.2.5-preview.3` tag at commit `d3d9652` immutable.
   Develop preview.4 as the narrow successor containing the MCP registration
   compatibility fix and its evidence; do not rewrite preview.3 history.
2. Move the default branch from its obsolete v0.2.2 state to the latest stable
   release lineage without making an unaccepted preview the advertised stable
   install.
3. Show stable and preview versions separately in the root README.
4. Make Package documentation and changelog destinations resolve to accurate
   release content instead of an obsolete default-branch file.
5. Keep every published tag immutable. Publish preview.4 as a prerelease only
   after its local release gates and real local Repair pass. Promote stable
   `v0.2.5` only after the required stable-closure work, upgrade matrix, and
   third-party acceptance pass.

## Deferred Environment Matrices

The following previously accepted risks remain independent live-validation
tasks. They are not silently converted to preview.3 implementation claims:

1. concurrent isolation between two independently configured Unity projects;
2. an Elevated Unity Editor queried by a NotElevated Codex/MCP client.

If the required environment is unavailable, record `BLOCKED` or `DEFERRED`,
never `PASS`. Stable release notes must continue to state the actual evidence.

## Non-Goals And Safety

- No v0.3.0 Discover Read expansion, global daemon, or global MCP registration.
- No automatic process termination, UAC manipulation, broad runtime deletion,
  downgrade, first-adoption overwrite of unknown content, or user-drift
  overwrite.
- The confirmed user recovery action is not authorization to rewrite unrelated
  `.codex/config.toml` content or delete outside its reviewed ignored Host and
  materializer runtime scope.
- Do not weaken root, ownership, reparse-point, process identity, generation
  lease, pipe authentication, transaction, or response-bound checks.
- Do not introduce version-control detection, command execution, authorization,
  user guidance, or Package-source-specific runtime branches.
- Do not commit credentials, tokens, Provider binaries, private machine paths,
  runtime reports, or machine-local configuration.
