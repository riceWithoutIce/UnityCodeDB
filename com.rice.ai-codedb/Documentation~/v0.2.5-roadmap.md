Status: `v0.2.5-preview.4` was published from commit `93912e2` and corrected the
preview.3 MCP descendant-table defect. Local focused MCP compatibility,
materializer, package boundary, payload hash closure, syntax, Unity 2022.3.20f1

Repair classified the unrelated live process as the old MCP solely because the

preview.3 and preview.4 tags remain immutable; the recovery fix and user-level

An earlier `v0.2.5-preview.5` working candidate completed local Repair, Uninstall,
Install, materializer, package-boundary, syntax, and Unity validation, but real
post-Install acceptance on 2026-08-15 exposed a new release blocker. A newly
created Codex task had the correct Unity project working directory and the
bundled CLI could parse and list the restored `codedb-project` registration,
but the task exposed zero `mcp__codedb_project__*` tools and could not call

The 2026-08-17 working tree is an unpublished implementation snapshot, not a

The earlier plan to deliver the complete thin Unity Bridge and external
Supervisor through `v0.2.5-preview.6` and `v0.2.5-preview.7` is superseded. The

## Frozen P0 Stabilization Contract (2026-08-15)

This section is authoritative wherever an older preview phase, backlog row, or
acceptance note conflicts with it. No new product capability enters
`v0.2.5` unless it is required for the normal user path, data/configuration
safety, or protection of external processes.

### P0 User Outcome

The one release-defining path is:

```text
Unity resolves the UPM Package
-> CodeDB prepares without requiring the Manager window
-> Install or automatic convergence completes
-> a new Codex task for that Unity project exposes mcp__codedb_project__*
-> codedb_status is callable and reports a usable project
-> a bounded text query succeeds
```

Host files, a current generation, a parseable `.codex/config.toml`, or a
successful `codex mcp list` are necessary evidence, but none alone proves the
user outcome. A preview cannot be called accepted or release-ready until the
real new-task path passes.

### P0 Product State

CodeDB tracks installation layers explicitly:

```text
INSTALLED -> CONFIGURED -> MCP_AVAILABLE -> READY
```

`INSTALLED` means Package-owned Host/runtime files are current. `CONFIGURED`
means the project registration is valid and ownership-safe. `MCP_AVAILABLE`
means the current Package-owned wrapper passes a real initialize and tool-list
probe from the project context. `READY` means those layers form one usable
project path; release acceptance additionally verifies the path from a real new
Codex task. The Manager must not reduce `INSTALLED` or `CONFIGURED` directly to
the user-visible `Ready` state.

The ordinary Manager surface exposes only `Starting`, `Ready`,
`Needs attention`, and `Uninstalled`. It presents at most one contextual
primary action. Generation, sequence, marker, lease, Host payload, MCP table,
script path, exit code, and process controls are diagnostics, not ordinary user
state.

### P0 User Actions

- The ordinary `Needs attention` recovery action is labeled `Reinstall CodeDB`.
  After second-level confirmation it creates and verifies a fresh isolated
  CodeDB instance, then atomically selects it. The user does not choose among
  Repair, Redeploy, Sync, Start, Stop, Restart, cleanup, or migration strategies.
- `Repair CodeDB` and `Fix CodeDB` are removed from the ordinary user surface.
  Their historical behavior remains regression evidence only; Install and
  Reinstall must not delegate to the legacy Repair orchestrator.
- `Install CodeDB` is shown only for an intentionally uninstalled project and
  must produce the complete user outcome without a second CodeDB action.
- `Uninstall CodeDB` remains available from a secondary menu with second-level
  confirmation. It completes logical project removal first, while leaving the
  UPM Package installed and preserving unrelated data and external clients.
  Retired physical state may remain `cleanup_state = PENDING` without blocking
  the visible `Uninstalled` result.
- Advanced diagnostics may expose technical state and a copyable diagnostic
  report. Advanced controls must never be a hidden prerequisite for install,
  upgrade, normal use, or recovery.

### P0 Release Gates

1. Start the Editor cold and enter Play immediately without opening Manager.
   Play must not wait for materialization, indexing, hashing, process startup,
   lock acquisition, or a complete status scan. Opening Manager first must not
   change the result.
2. Complete real Install, Upgrade, and confirmed Reinstall instance publication
   with no manual file edit, PID or lease cleanup, global registration,
   client-process termination, or second CodeDB action. Reinstall must remain
   usable even when an untrusted legacy watcher cannot be stopped or cleaned.
3. Run the final Package-only acceptance in a standalone Unity project outside
   the UnityCodeDB source repository, with no unrelated user-level CodeDB
   registration participating in the result. Record the exact Unity, Package,
   Host-generation, Codex Desktop, working-directory, process, and tool-list
   evidence.
4. Keep materializer regression, package boundary and hash closure, syntax,
   Unity EditMode, transaction, ownership, and external-process safety gates.
   They support but do not replace the real user path.
5. Freeze one candidate snapshot before concentrated review. Findings are
   returned once; development is not interrupted by incremental audit tasks.
   The user performs one final golden-path acceptance only after the snapshot
   passes its owned gates.

### P0 Non-Goals

- No complete thin Bridge/external Supervisor migration, versioned Supervisor
  IPC, general query-first queue, `CORE_READY` protocol, Domain Reload reconnect,
  or full background-work architecture in `v0.2.5`. Those are `v0.3.0` work.
  The immutable instance/control foundation, atomic Package handoff, serialized
  install operations, cached progress, and the bounded work needed to keep cold
  Play responsive are deliberately pulled forward because the P0 user paths
  cannot be made reliable without them.
- No concurrent two-Unity or Elevated-Unity/NotElevated-MCP acceptance in this
  closure; both remain explicitly deferred.
- No theoretical race hardening, TOML-format exhaustiveness, rare historical
  state expansion, style refactor, or new developer maintenance command unless
  it closes a demonstrated P0 safety or normal-path failure.
- No new preview publication after each internal fix. The next preview contains
  the complete frozen P0 and is published only after its local gates pass.

## One-Action Installation Contract (2026-08-17)

This section supersedes older wording that treats Setup, Repair, Manager
interaction, copied Provider files, or internal scripts as part of the normal
installation or upgrade path. The supported clean environment is a prepared
Windows machine with a supported Node.js runtime and a compatible CodeDB
Provider, plus a standalone Unity project. Node.js and Provider are machine
prerequisites; the Unity project does not need Git, SVN, Perforce, or any other
version-control system.

The user perceives one action for each normal path:

```text
First installation:
UPM install -> Unity compile/reload -> automatic CodeDB convergence
-> new Codex task -> tools -> usable status -> bounded query

Upgrade installation:
v0.2.4 -> one UPM Update -> Unity compile/reload
-> automatic generation handoff -> new Codex task
-> tools -> usable status -> bounded query
```

Changing `manifest.json` or selecting Update in Package Manager are equivalent
Package-selection inputs. After Unity has resolved the selected Package, CodeDB
must not branch on how it was installed. Neither normal path may require the
Manager window, `Fix CodeDB`, `Repair CodeDB`, a second CodeDB button, a maintenance script,
manual TOML editing, PID or lease cleanup, closing an old MCP task, terminating
a process, or copying Provider files into the project.

An upgrade with an active old MCP keeps that session and its immutable
instance alive, publishes and selects a new verified instance for future tasks,
and reclaims the retired instance only after its lease drains. A legacy process
whose ownership cannot be authenticated does not block creation or selection of
the disjoint new instance; it is never force-stopped and is left to exit
naturally. The upgrade must not ask the user to close the old task and must never
terminate an external MCP client.

The machine Provider contract is versioned and verifiable:

```text
%LOCALAPPDATA%\Rice\CodeDB\providers\<version>\
|- codebase-mcp.exe
`- provider-manifest.json
```

The manifest records Provider version and commit, SHA-256, protocol
compatibility, source, and supported Package range. A missing or unsupported
Node.js runtime, missing Provider, invalid manifest, incompatible protocol, or
hash mismatch is `Missing prerequisite`. It yields one user-facing prerequisite
instruction and zero project mutation; it must not enter a repeated Repair or
automatic-retry loop.

## Product Decision

After Unity successfully resolves and loads the Package, CodeDB must behave the
same regardless of how the Package arrived or whether the Unity project uses
Git, SVN, Perforce, another version-control system, or none. Package runtime
logic must not detect, invoke, or branch on a version-control system or Package
installation source. It must reconcile every package-owned project state that
can be changed safely without requiring the Manager window, Sync, process
termination, PID cleanup, lease cleanup, authorization JSON, or deletion of
unrelated runtime data.

First Install, automatic Upgrade, and confirmed Reinstall use one immutable
instance deployment engine. Every operation performs read-only preflight,
creates a fresh candidate instance, verifies initialize, exact tools, usable
status, and a bounded query against that candidate, atomically publishes
`current-instance.json`, and retires the previous instance for asynchronous
cleanup. A failed candidate is discarded or quarantined without changing the
selected instance; an interrupted activation recovers from the durable operation
journal and last-known-good pointer.

The project runtime contract is rooted under `AIWork/.runtime/codedb/`:

```text
control/
|- desired-state.json
|- current-instance.json
|- last-known-good-instance.json
`- operation.json
host/generations/<generation-id>/
instances/<instance-id>/
|- instance.json
|- config/
|- index/
|- adapter/
|- watch/
|- leases/
|- logs/
`- tmp/
```

Each Reinstall receives a new instance identity, runtime path, pipe, lease set,
and disposable derived state. It preserves user policy, reviewed custom
configuration, business files, unrelated TOML, and the verified machine
Provider. It recreates index, adapter, watcher, MCP-availability evidence, and
other Package-derived state. The new runtime contract advances to immutable Host
generation `poc.32`; existing `poc.31` identity and every published generation
remain unchanged.

An active or untrusted legacy watcher is retirement work, not an activation
dependency. If it cannot be authenticated, CodeDB neither stops it nor reuses its
runtime identity; the new instance uses disjoint paths and transport identity.
Only a candidate collision with an unowned target, path escape, reparse point,
or mutation of unrelated bytes may block before activation. Cleanup failure is
reported separately and never turns a usable selected instance into a failed
Reinstall.

The Manager exposes a separately confirmed `Uninstall CodeDB` action
from a secondary menu. It removes or retires the project integration while
keeping the UPM Package installed so the Manager can offer a later clean
Install. Logical uninstall publishes the desired state and disables current
registration/selection before best-effort physical retirement. Package
self-removal remains Unity Package Manager's responsibility.

Instance publication remains fail-closed for real CodeDB-owned file drift, unowned
path collisions, invalid manifests, path escapes, unsupported bootstrap
transitions, and downgrades. Safety derives only from the canonical project
root, Package manifest and allowlist, CodeDB ownership marker, byte hashes,
project lock, durable transaction and rollback, reparse-point checks, generation
leases, and explicit confirmation where required. Manual Start, Stop, Restart,
automatic-start policy, and automatic-update policy remain independent
diagnostic controls and must not enter the ordinary user path.

## Target Runtime Architecture Decision (v0.3.0)

`v0.3.0` consumes the `v0.2.5` instance/control layout, atomic activation,
Package handoff, rollback, and retired-instance contract. It does not redesign
those foundations. Its runtime work begins at the Unity Bridge, versioned IPC,
external Supervisor, general scheduling, reconnect, and shutdown layers.

Unity Editor integration is a thin Bridge, not the CodeDB runtime host. Work on
the Unity main thread is limited to receiving Unity lifecycle signals, reading
Unity's resolved Package location, rendering UI, collecting explicit user
confirmation, and atomically enqueueing an in-memory command or event. The
Bridge must not perform filesystem I/O, persist leases, hash payloads, launch or
wait for processes, invoke PowerShell or Node, wait for locks, perform
synchronous IPC, or calculate a complete CodeDB status.

A background IPC worker connects the Bridge to one project-local external
Supervisor. The preferred implementation extends the existing Node coordinator
instead of introducing another persistent runtime. The Supervisor owns process
lifecycle, durable state, indexing schedules, Package handoff, recovery
coordination, and cached status. It is scoped by canonical project identity and
records the owning Editor PID plus process-start identity so a reused PID cannot
be mistaken for the owning Editor. It is not a machine-global daemon, Windows
service, or global MCP registration.

The Package-owned instance deployment engine remains an independent one-shot
fallback for Install, confirmed Reinstall, and confirmed Uninstall when the
Supervisor is unavailable. It is not part of every healthy Editor startup.
Domain Reload
reconnects the Bridge and does not restart healthy backend processes. Entering
Play keeps the query path available while heavy maintenance pauses or defers.
Final Editor exit stops the project coordinator, Provider, and adapter after
identity checks; it never terminates a dormant or external MCP wrapper/client.

## Confirmed Preview.3 MCP Registration Defect

The third-party project contains this legal TOML shape:

```toml
[mcp_servers.codedb-balance]
command = "node"
args = ["AIWork/codedb/wrapper/codedb-balance-wrapper.mjs", "--root", "."]
startup_timeout_sec = 120

[mcp_servers.codedb-balance.tools.codedb_text_search]
approval_mode = "approve"
```

A standards-compliant TOML parser accepts it, but preview.3 reports
`ambiguous dotted-key collision for mcp_servers.codedb-balance`. The current
MCP merge preflight mistakes a legal descendant table for a collision with the
target server table, and the materializer regression suite encodes that wrong
expectation.

The ownership boundary is narrower than the current parser assumes. CodeDB
owns only these direct keys in the target server table:

- `command`
- `cwd`
- `args`
- `startup_timeout_sec`

Other direct keys and descendant tables, including `tools.*`, are user- or
client-owned and must remain byte-preserved unless they create a real TOML
namespace conflict with one of the four managed keys. A target scalar, target
array table, duplicate target declaration, or a managed key declared as a
table remains an unsafe conflict and must fail closed.

The phases below replace the earlier preview.4-preview.7 execution order. They
do not erase the historical defects documented later in this file; they define
the only remaining delivery order for `v0.2.5-preview.5`. Full thin-Bridge and
Supervisor work remains in `v0.3.0`.

### Phase 0: Plan Synchronization And Snapshot Checkpoint

1. Synchronize this route with GitHub Project 7 before dispatching more code.
2. Record the current dirty implementation snapshot and map existing work to
   the phases below without resetting, rewriting, or prematurely publishing it.
3. Freeze the two normal user paths, prerequisite contract, safety boundaries,
   test layers, deferred matrices, and the single `preview.5` release target.

Exit: roadmap and Project tasks agree, current evidence is labeled accurately,

### Phase 1: Machine Prerequisite Contract

1. Define the supported Node.js range and the versioned machine Provider
   location and manifest schema.
2. Validate Provider identity, SHA-256, protocol compatibility, source, and
   supported Package range before project mutation.
3. Reduce missing or incompatible Node.js/Provider state to one
   `Missing prerequisite` result and one user action; do not invoke Repair or
   copy a Provider into each Unity project.

Exit: valid prerequisites permit planning; invalid prerequisites produce zero
project writes, no process termination, and no retry loop.

### Phase 2: Immutable Instance And Control Contract

1. Introduce the versioned `control/`, `host/generations/`, and
   `instances/<instance-id>/` layout and one stable Package-owned wrapper that
   resolves only the atomically selected current instance.
2. Use one provision, verify, activate, rollback, retire, and result engine for
   first installation, automatic upgrade, confirmed Reinstall, Install, and
   Uninstall. Policy may authorize different plans; state interpretation and
   safety checks may not diverge.
3. Create every candidate in a new isolated instance with unique paths, pipe,
   leases, logs, temporary state, and derived caches. Verify the candidate before
   changing `current-instance.json`; never repair an active instance in place.
4. Keep Package source read-only and installation-source/VCS independent.
   Preserve project locks, path and reparse checks, ownership/hash closure,
   durable journal, last-known-good rollback, unrelated configuration, and
   external-process safety.
5. Advance the new runtime contract to immutable Host generation `poc.32` and
   retain every existing generation identity byte-exact.
6. Make every operation idempotent and globally serialized per project. A retry
   after interruption recovers the operation journal or returns a stable safe
   result; lifecycle events coalesce instead of starting overlapping work.

Exit: deterministic fixtures prove candidate isolation, pre-activation
verification, atomic selection, rollback, interruption recovery, idempotency,
and retirement that cannot corrupt the active or last-known-good instance.

### Phase 3: Clean-Project First Installation

1. After UPM resolves the Package and Unity finishes compile/reload, schedule
   automatic convergence without requiring Manager to open.
2. Provision a fresh candidate instance, create ownership-safe project MCP
   registration through the stable wrapper, verify actual candidate status and
   a bounded query, then atomically select it.
3. Keep startup and immediate Play responsive. Long filesystem, hash, process,
   lock, PowerShell, Node, or complete-status work must not synchronously block
   Unity lifecycle callbacks or Manager rendering.
4. Present `Ready` only when installation, registration, MCP availability, and
   usable status agree.

Exit: one UPM install yields a queryable new Codex task with no second CodeDB
action, manual file operation, or project-local Provider copy.

### Phase 4: v0.2.4 One-Action Instance Handoff

1. Treat one UPM Update or equivalent Package selection as the only user action;
   compile/reload triggers automatic convergence to the selected Package.
2. Treat the v0.2.4 flat/runtime layout as a legacy source. Provision and verify
   a disjoint preview.5 instance before switching the stable wrapper; never
   mutate the legacy runtime in place.
3. Cover no active old MCP, authenticated active old MCP, and an unauthenticated
   legacy watcher. Existing clients remain on the old execution closure while
   new tasks select the verified new instance. An unauthenticated owner is not
   force-stopped and does not block a disjoint activation.
4. Preserve valid custom configuration and unrelated data. Retire the legacy
   closure after natural lease/process drain without another user action.
5. On candidate verification or activation failure, retain or restore the last
   known good instance and report one stable result. Never require PID/lease
   cleanup or terminate an external MCP client.

Exit: both upgrade paths produce a queryable new Codex task after one Package
update, and rollback leaves the previous usable installation intact.

### Phase 5: Reinstall, Logical Uninstall, And User Surface

1. Produce one read-only readiness snapshot from prerequisite, installed,
   configured, MCP-available, usable-status, and cleanup evidence. This snapshot
   describes current product state; it does not infer mutation success.
2. Return one versioned result from every mutating operation, including outcome,
   phase, candidate/current instance identity, reason, activated scopes, cleanup
   state, and one next action. A successfully activated instance is successful
   even when retired cleanup remains pending.
3. Combine the readiness snapshot and latest validated operation result through
   one user-state reducer. Do not implement competing lifecycle, action, and UI
   reducers.
4. Keep ordinary UI at `Starting`, `Ready`, `Needs attention`, `Uninstalled`,
   and `Missing prerequisite`, with at most one contextual primary action.
   `Needs attention` offers `Reinstall CodeDB`; `Uninstalled` offers
   `Install CodeDB`; a missing prerequisite shows its prerequisite guidance.
5. Keep diagnostics copyable and transparent, but never make technical controls
   or internal state names part of a required normal workflow.
6. Remove ordinary `Fix CodeDB` and `Repair CodeDB`. Confirmed Reinstall creates
   a fresh instance and atomically switches only after verification; it never
   invokes legacy `Invoke-Repair`. Secondary confirmed Uninstall publishes
   logical `UNINSTALLED` before best-effort physical cleanup.
7. Keep Manager and lifecycle operations asynchronous and single-flight. Render
   cached progress; compilation, Package update, and Play transitions must not
   synchronously wait for instance creation, verification, cleanup, PowerShell,
   Node, process startup, filesystem scans, or locks.

Exit: UI and lifecycle use the same result, do not claim false Ready, and do not
ask the user to choose a maintenance strategy.

### Phase 6: Development-Owned Validation

1. Run the layered strategy below. Per-change runs use quick static gates and
   the affected deterministic subset; the full regression runs once on a frozen
   code snapshot, not after every documentation or task update.
2. Complete fresh local Unity integration before publishing a Package artifact.
   Include real Manager Install/Reinstall/Uninstall UI, candidate progress,
   logical-uninstall cleanup pending, cold immediate Play, and Manager-unopened
   behavior; compile or direct script probes do not replace this evidence.
3. Log every internal command with purpose, affected paths/processes, and exit
   code. Internal commands and direct wrapper probes are engineering evidence,
   never substitutes for real Package or Codex-task acceptance.
4. Development owns scripts, fixtures, logs, and environment preparation. The
   user is not asked to execute engineering test scripts.

Exit: all owned gates pass or are explicitly `BLOCKED`; no failed, deferred, or
historical result is promoted to `PASS`.

### Phase 7: One Candidate And Two Golden Paths

1. Publish one `v0.2.5-preview.5` candidate only after Phases 1-6 pass on one
   frozen snapshot. Do not allocate preview.6 or preview.7 in advance.
2. Internally install the released artifact in standalone projects and execute
   first install, no-active-owner upgrade, active-old-MCP upgrade, confirmed
   Reinstall, and logical Uninstall/Install coverage.
3. Ask the user for exactly two normal-product flows: one clean UPM install and
   one v0.2.4 UPM Update while the old MCP task remains open. Fold the cold Play
   and real new-task status/query observations into those flows. No separate

   user acceptance.
4. Concentrate review once. If either golden path fails, record the observed
   failure against this candidate and return to the owning phase before deciding

5. Decide stable `v0.2.5` only after both golden paths pass. Two-project

### Layered Test Strategy

Coverage is selected by failure class, not by multiplying every state, Package
source, process state, Unity event, and recovery action into an exhaustive
matrix. Each release-critical class receives a representative normal case and
at least one bounded failure case; rollback and idempotency are added where the
class can mutate state.

- `L0 - Quick contract gates`: syntax, package boundary, identity/hash closure,
  forbidden runtime dependency scans, and compile checks. Run after each
  relevant change.
- `L1 - Deterministic engine tests`: focused inventory/planner/transaction,
  instance provision/verify/activate/retire, registration preservation,
  lease/process safety, rollback, and idempotency fixtures. Run the affected
  subset per change and the full suite once per frozen code snapshot.
- `L2 - Fresh local Unity integration`: compile/EditMode plus cold startup,
  immediate Play, Manager-open parity, real Reinstall/Uninstall UI, and automatic
  convergence in a disposable project. Run before candidate publication.
- `L3 - Released Package artifact`: install the exact prerelease artifact in
  standalone projects and execute first-install, v0.2.4-upgrade, and Reinstall
  paths. Local source or copied payload success cannot replace this layer.
- `L4 - Third-party user golden paths`: repeat the two normal paths with real
  Unity Package Manager and real new Codex tasks. This is the final user-facing
  evidence and is never inferred from L0-L3.

Manual acceptance is intentionally small and outcome-oriented. The two L4 user
flows include Package install/update, cold immediate Play, and a new Codex task
tools/status/query check. Reinstall and Uninstall are exercised as real UI paths
by development at L2/L3 rather than added as a third user golden path. No manual
flow inspects journals, markers, hashes, leases, PIDs, or internal directories
unless a failure needs developer-owned diagnosis.

## Confirmed Preview.2 Defect

The tracked ownership marker can arrive through Git claiming the current
package generation is installed while `AIWork/.runtime/` remains absent or on
an older generation because that directory is intentionally ignored. The
preview.2 materializer treats the resulting missing and older runtime files as
`ManagedMissing` or `ManagedDrift`, converts them to `CONFLICT`, and refuses the
safe package reconstruction.

The Editor then requires `current.json` to match the current Package identity,
classifies an otherwise valid previous generation as `Invalid`, redirects Host
paths under `host/unavailable`, and still exposes actions that attempt to run
scripts there. Persisted `upgrade-state.json` can simultaneously report a stale
older generation as green `CURRENT`.

Preview.2 also calls `git rev-parse` while planning a DryRun. In Windows
PowerShell 5.1, the expected native failure for a non-Git project is promoted to
a terminating error by the script's global stop policy before the optional Git
result can be handled. Strict first-adoption Sync and Remove additionally bind
authorization to a Git worktree, HEAD, index, and ignored authorization file.
That makes version control an accidental product prerequisite. Preview.3 must
remove the prerequisite and all version-control command execution from Package
runtime behavior; merely suppressing the DryRun error is insufficient.

## Retained Preview.2 Scope

The controlled legacy Redeploy path introduced in preview.1 and completed in
preview.2 remains part of v0.2.5. Published byte-exact `poc.9`, `poc.16`, and
`poc.20` flat Hosts must still receive focused active-owner guidance, allow the
Manager to stop only a recognized legacy watcher, refuse to terminate external
MCP clients, publish the current generation transactionally, and regenerate
only the reviewed ignored runtime config. Preview.3 must retain this coverage
while advancing the target generation from `poc.29` to `poc.30`.

## Preview.3 Required Scope

### Portable Adoption And Runtime State

1. Introduce a portable CodeDB ownership-marker contract that records project
   adoption, requested package/payload identity, and only package-owned stable
   Host-file ownership. Its trust does not depend on how the project was copied,
   archived, installed, or versioned.
2. Stop using the portable marker as proof that local generation files or
   `current.json` exist on the current machine.
3. Derive actual runtime installation state from the selected pointer,
   generation manifest, package-managed generation closure, leases, and
   materializer diagnostics under ignored runtime.
4. Read existing schema-1 markers compatibly. Runtime entries in a schema-1
   marker may establish historical package intent but cannot turn ordinary
   local-runtime absence or a valid older pointer into user drift.
5. Permit first adoption to converge automatically when every CodeDB-managed
   target is absent and all project, manifest, path, and configuration preflight
   checks succeed. If a current installation needs recovery, offer confirmed
   `Reinstall CodeDB`, which provisions a separate candidate rather than
   mutating the failing installation. Neither path may require version-control
   metadata, commands, tools, or authorization JSON.

### Automatic Runtime Reconstruction

After Package resolution or script reload, automatically reconcile these
project states:

- a fresh project has no marker and every CodeDB-managed target is absent;
- portable Host and marker are current while local runtime is absent;
- portable Host and marker are current while a valid older generation remains;
- a known lower portable marker and matching lower generation both remain;
- the current package generation already exists byte-exact but the marker or
  pointer publication is incomplete;
- a recoverable automatic-upgrade transaction was interrupted.

The automatic path must acquire the project-local materializer lock, re-check
ownership, stage on the same volume, validate the complete manifest and hashes,
publish the immutable generation, retain a validated last-known-good pointer,
switch `current.json` atomically, and complete watcher handoff. Existing MCP
requests stay pinned to their leased generation and are never terminated.

Do not auto-repair a partially present candidate generation with unexpected
bytes, an invalid previous pointer, unmanifested generation content,
CodeDB-owned Host drift, or a path/identity collision. Report the exact boundary
instead with byte-exact zero writes outside recoverable transaction evidence.

### Version-Control And Installation-Source Independence

1. Package runtime and Editor code must not execute or probe `git`, `svn`,
   Perforce, or another version-control command. It must not inspect worktrees,
   repositories, HEAD/revisions, indexes, staging, ignore rules, or installation
   URLs to authorize or classify a CodeDB action.
2. DryRun, first Install, automatic Upgrade, Reinstall, Verify, and Uninstall
   must use the same CodeDB-owned state machine in projects with or without
   version-control metadata and when version-control executables are absent from
   `PATH`.
3. Remove the tracked-host authorization JSON contract from the supported
   product workflow. Confirmation authorizes only the exact manifest-closed
   CodeDB scope; it never authorizes overwriting unknown or drifted content.
4. Resolve Package payloads from Unity's loaded Package location without
   assuming a fixed source layout or writable Package directory. Never mutate
   Package source content.
5. Treat unknown same-name files, malformed ownership evidence, drift, path
   escapes, reparse points, active unsafe owners, and ambiguous MCP configuration
   as CodeDB safety conflicts. Refuse with focused guidance and zero unrelated
   writes; do not ask the user to initialize or change version control.
6. Keep all user-facing status and recovery guidance free of Git, SVN, staged,
   HEAD, checkout, and authorization-file prerequisites.

### Generation And Status Truth

1. Validate pointer and generation integrity independently from whether their
   Package version is the currently loaded Package.
2. Represent a complete compatible lower generation as `PREVIOUS` or
   `UPGRADE_PENDING`, not `Invalid`.
3. Reserve `Invalid` for malformed identity, unsupported protocol, path escape,
   missing closure, hash drift, or unmanifested generation content.
4. Correlate persisted upgrade state with the loaded target generation. An
   older `CURRENT`, `CHECK_FAILED`, or transient phase is historical/stale and
   cannot be rendered as the current update result.
5. Validate last-known-good semantics before reporting it as retained.

### Manager And Command Safety

1. Centralize the readiness gate for every command that resolves a Host script.
2. Never construct or execute `host/unavailable/scripts/...`.
3. Disable Prepare, Regenerate, Verify, Provider Guidance, index, watcher, and
   registration actions while their required generation is unavailable.
4. Present `UPGRADE_PENDING`, `REBUILD_REQUIRED`, `INSTALLING`, `SWITCHING`,
   `DRAINING`, `CURRENT`, `ROLLBACK`, `CHECK_FAILED`, `CONFLICT`, and
   `DOWNGRADE_REVIEW_REQUIRED` without contradictory green rows.
5. Retain one manual `Update now` or `Retry update` fallback when automatic
   mutation is disabled or a deterministic failure requires review.

### One-Click User Recovery (`Reinstall CodeDB`)

The Manager exposes one ordinary recovery action, `Reinstall CodeDB`, only in
`Needs attention`. It replaces the Repair/Fix strategy selector with a clean
instance replacement that does not depend on proving that every historical
process or derived file can be cleaned first. Existing Inspect, Verify, Sync,
Remove, Redeploy, registration-draft, and validation commands may remain as
diagnostics while migration is in progress, but none is a supported user
recovery step and Install/Reinstall must not call `Invoke-Repair`.

1. One click opens a second-level confirmation dialog. It states that CodeDB
   will create and validate a fresh project-local instance, preserve user-owned
   data and configuration, switch future sessions only after validation, and
   retire old Package-owned state in the background. `Cancel` is byte-exact zero
   write; the primary confirmation is `Reinstall CodeDB`.
2. After confirmation, run one serialized operation: read-only preflight,
   allocate a new instance identity, provision its runtime and generated state,
   create or update only the owned project MCP registration, run initialize,
   exact tools/list, usable `codedb_status`, and bounded
   `codedb_text_search`, then atomically publish the new current-instance pointer.
3. Candidate failure leaves the old selected/last-known-good instance and MCP
   registration usable. Activation interruption is recovered through the
   durable operation journal. Repeating Reinstall creates at most one committed
   replacement for the operation and converges idempotently.
4. Every Reinstall creates a new runtime path, pipe identity, lease scope,
   watcher state, MCP-availability evidence, index, and adapter state. Preserve
   the machine Provider, user policy, reviewed custom runtime configuration,
   business files, unrelated generations/instances, version-control metadata,
   and unrelated `.codex/config.toml` bytes.
5. Never terminate an external MCP client. An authenticated previous instance
   remains available until its lease drains. An unauthenticated legacy watcher
   is neither stopped nor treated as a prerequisite; disjoint instance and pipe
   identities allow the new activation to proceed, and cleanup waits for natural
   exit. Only an unavoidable target collision or unsafe ownership/path boundary
   blocks before activation.
6. Create or update only `[mcp_servers.<project-slug>]` in the trusted project
   `.codex/config.toml`, using the stable Package-owned wrapper, `cwd = "."`,
   `--root "."`, and bounded startup timeout. Preserve all unrelated tables,
   keys, comments, ordering, BOM, and line-ending style. Invalid TOML, duplicate
   target tables, or ambiguous collision remains zero-write blocked.
7. Finish with `REINSTALLED`, `BLOCKED`, or `CANCELLED`, plus the operation
   phase, selected/candidate identity, `cleanup_state = COMPLETE|PENDING`, and
   one next user action. There is no ordinary `PARTIALLY_REPAIRED` state. A
   verified active instance with retained retirement work is
   `REINSTALLED/PENDING` and requires no cleanup action from the user. Do not
   claim that an already running Codex client hot-reloaded the new registration.

### User-Visible Project Uninstall

`Uninstall CodeDB` is a separately confirmed secondary-menu action and an
explicit user escape hatch. It is not the normal upgrade path and does not
remove the UPM Package that supplies the Manager. Advanced diagnostics are not
required to reach it.

1. Atomically publish the project integration desired state as `UNINSTALLED`,
   remove the current project's CodeDB-managed MCP registration keys, and clear
   active instance selection before physical cleanup. Editor load, Domain Reload,
   and Package update reconciliation must respect it and must not silently
   reinstall CodeDB.
2. After logical uninstall is durable, gracefully stop an authenticated
   Package-owned watcher and remove or retire only manifest-closed CodeDB-owned
   instance/Host state. Stop refusal, an unauthenticated legacy owner, sharing
   violation, or retained lease changes only `cleanup_state`; it does not roll
   the project back to an installed or failed state.
3. Preserve unrelated `.codex/config.toml` bytes, Provider, indexes, adapters,
   custom runtime configuration, existing user policy, Package source, unrelated
   project files, and every external process.
4. If an external MCP still owns an execution closure, finish the logical
   uninstall, retain that closure, and return `UNINSTALLED` with
   `cleanup_state = PENDING`. Reclaim it automatically after lease drain; do not
   ask the user to close a PID, delete a lease, or click a second action.
5. Cancellation is byte-exact zero write. Interrupted and repeated Uninstall
   resumes idempotently through the same transaction engine.
6. The uninstalled Manager state exposes one `Install CodeDB` action. Confirmed
   Install clears the desired state only as part of successful activation and
   creates a fresh project integration through the immutable candidate engine.
   It must not reuse stale derived state or invoke the legacy Repair workflow.
7. Actual removal of `com.rice.ai-codedb` from `Packages/manifest.json` remains
   a Unity Package Manager operation and is outside this v0.2.5 button.

### Downgrade And Package Selection Changes

1. Never downgrade automatically.
2. Detect a valid runtime generation newer than the Package currently loaded by
   Unity instead of misclassifying it as user drift. The result cannot depend on
   how that Package version was selected.
3. Offer a confirmed, project-scoped rebuild/switch to the selected Package
   only after active MCP and watcher owners have drained.
4. Preserve Provider binaries, indexes, adapters, runtime configuration,
   policies, registration, unrelated generations, and unrelated project files.
5. Keep a valid rollback pointer and never let an older Package delete an
   unvalidated newer generation through a broad cleanup path.

### Metadata-Only Package Updates

1. Treat Package version metadata separately from Host compatibility identity.
2. When payload sequence, generation, bootstrap protocol, manifest closure, and
   hashes are identical, a Package-only version change must not invalidate the
   selected generation or require a fabricated Host migration.
3. Reusing one payload sequence with different identity or bytes remains a
   sequence collision and must fail closed.
4. Add a release gate that verifies Package, payload, generation, pointer,
   Editor constants, changelog, and tag identities before publishing.
5. Preview.3 still advances to `poc.30` because its materializer and Host
   contract change; metadata-only support applies to future releases.

### Runtime Configuration Migration

1. Automatically replace a runtime config only when it is byte-exact to a known
   previously generated template and the new template is compatible with the
   retained project/provider identity.
2. Never silently overwrite a customized runtime config.
3. Customized incompatible configuration reports one focused reviewed action;
   it does not block package-owned Host reconstruction when the old backend can
   remain safely retained.
4. Preview.3 must leave existing config, Provider binaries, indexes, adapters,
   MCP registration, manual runtime state, and update/start policies byte-exact
   when no config-schema migration is required.

### Retry And Recovery Policy

1. Retry project-lock contention, a concurrently running upgrade, and bounded
   transient Windows sharing races with capped backoff.
2. Do not permanently suppress automatic reconciliation for failures that made
   no unsafe mutation and are classified as transient.
3. Suppress repeated automatic mutation for deterministic validation failure,
   watcher handoff rollback, incomplete rollback, drift, or collision; expose
   the persisted reason and manual retry.
4. Recover durable automatic-upgrade journals before starting another mutation.

## v0.2.5 Release Acceptance Scenarios

The following nine scenarios are the complete release-level coverage set for
`v0.2.5-preview.5`. Detailed internal fixtures may cover more input variants,
but they do not expand the user's acceptance script or create a Cartesian test
matrix.

1. Fresh standalone Unity project, supported Node.js and valid Provider: one
   UPM install converges automatically and a real new Codex task exposes tools,
   usable status, and a bounded query.
2. `v0.2.4 -> v0.2.5-preview.5` with no active old MCP: one UPM Update converges
   automatically and the new task uses the new generation.
3. The same upgrade with an active old MCP: the old task remains alive on its
   leased generation, the new task uses the new generation, and cleanup waits
   for natural lease drain.
4. Missing Node.js: one `Missing prerequisite` state, zero project mutation,
   and no mutation/retry loop.
5. Missing, invalid, hash-mismatched, or incompatible Provider: one
   `Missing prerequisite` state, zero project mutation, and no per-project copy.
6. Cold immediate Play with Manager never opened, then with Manager opened:
   both remain responsive and have equivalent CodeDB lifecycle results.
7. Real new Codex task validation: correct project cwd, actual
   `mcp__codedb_project__*` tools, callable usable `codedb_status`, and one
   bounded `codedb_text_search`. Config parsing or a direct wrapper probe alone
   is insufficient.
8. Confirmed Reinstall provisions and verifies a new instance before activation,
   remains usable when an unauthenticated legacy watcher cannot be cleaned, and
   reports retained retirement work as `REINSTALLED/PENDING`. Confirmed Uninstall
   reaches durable `UNINSTALLED/PENDING` before best-effort cleanup, and its one
   Install action creates another fresh instance.
9. Representative failure safety: injected publication failure rolls back;
   repeated convergence is idempotent; unrelated TOML/config bytes and Package
   source remain unchanged; active external MCP and unrelated processes remain
   alive.
