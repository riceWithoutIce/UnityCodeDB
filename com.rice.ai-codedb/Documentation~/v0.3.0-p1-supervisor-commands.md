# v0.3.0 P1-B: Project Supervisor Command Ownership

Status: implementation snapshot; not release evidence.

## Purpose

P1-B moves project command ownership out of Unity callbacks. A project-local
Node Supervisor owns the command pipe, maintenance admission, query lane,
cached readiness, and the lifecycle of the atomically selected immutable
instance. During a Package-declared transition, that selection may be the
current generation or one exact `TRUSTED_PREVIOUS` generation. Unity consumes
the authenticated snapshot and submits commands asynchronously through the
Bridge.

## Runtime Contract

The Supervisor runtime is stored below the consuming project:

```text
AIWork/.runtime/codedb/control/supervisor/
  supervisor-state.json
  supervisor.lock
  supervisor-events.jsonl
  supervisor-error.json
```

The state file is project, selected-instance, generation, runtime, and pipe
bound. The Bridge requires strict UTF-8 JSON, exact schema/type checks, the
expected project identity, a Package-classified current or trusted-previous
instance, and the derived Windows pipe name before sending a command. Pipe
identity hashes lowercase forward-slash canonical project/runtime paths in both
C# and Node. The original protocol-v1 native-path hash is recognized only as a
bounded compatibility identity so an already authenticated Supervisor can
complete one handoff. The Supervisor and coordinator use independent IPC
tokens; the outer Bridge token is never forwarded to the coordinator.

An exact trusted-previous instance continues to receive its Editor lease while
the candidate is prepared. When a successful materializer operation atomically
changes `current-instance.json`, the old Supervisor queues its own shutdown,
stops only its authenticated Package-owned coordinator, removes its control
state, and lets the next Bridge request start a Supervisor bound to the new
instance. The Bridge also requests the existing authenticated `shutdown`
command for an older protocol-v1 process that predates self-handoff. Neither
route stops or rewrites an external MCP client or its immutable leased closure.

Supported command lanes are:

- query/status observations, which use the query lane;
- reconcile, watcher maintenance, and materializer operations, which use the
  serialized maintenance lane;
- shutdown, which only requests an authenticated project-owned coordinator to
  stop.

Maintenance commands never keep one IPC stream open while PowerShell, watcher,
or coordinator work runs. The authenticated request performs bounded admission
only and returns `accepted`, `pending`, an opaque `operation_id`, the current
`event_sequence`, and cached status. The Supervisor then executes the operation
on its serialized maintenance lane and persists both running and terminal
operation evidence in `supervisor-state.json`. The Bridge uses separate bounded
`operation` requests to observe that exact identity until it reaches
`completed` or `failed`; every pipe exchange retains the short control-plane
deadline. The materializer's own bounded execution window is not an IPC read
timeout.

This operation model is `supervisor_protocol_version: 2`; the outer envelope
remains protocol version 1. A Package reload that observes an authenticated
Supervisor protocol 1 waits for its already admitted maintenance operation to
finish, requests its owned shutdown, waits for the control lock to retire, and
starts protocol 2 from the same validated selected instance. Unknown protocol
versions remain blocked. The compatibility handoff never kills a process or
removes an external MCP lease.

A repeated request with the same operation key reuses the running operation
rather than launching another PowerShell process. A different maintenance key
receives `SUPERVISOR_BUSY` and cannot bypass single-flight ownership. Play or
Domain Reload may cancel the Unity-side waiter without canceling the admitted
Supervisor operation; a later Bridge connection can reattach by submitting the
same operation key and polling the returned identity. Terminal failure output
is retained as the command result instead of being reduced to a transport
timeout.

When a completed materializer operation changes `current-instance.json`, its
terminal result carries `handoff_queued`. Observing that terminal state retires
the authenticated old Supervisor; a short unobserved-handoff grace also retires
it when the Unity waiter disappeared during Domain Reload. This grace is a
lifecycle handoff bound, not an extension of the per-request IPC deadline.

The Supervisor never terminates an external MCP client. A reviewed one-shot
materializer fallback remains only for a proven empty-runtime bootstrap. A
transport outage, startup failure, watcher command, or invalid/ambiguous
Supervisor evidence is blocked rather than silently starting a second command
owner.

## Unity Boundary

`AICodedbSupervisorLauncher` starts the Supervisor from a worker task after the
current immutable instance has been validated. `AICodedbEditorLifecycle`
routes reconcile and watcher work through the Supervisor and keeps lease and
status work on its background scheduler. `AICodedbManagerWindow` consumes the
cached lifecycle result and queues user actions; opening or repainting the
Manager does not synchronously start a Provider, run PowerShell, hash a Host,
wait for a lock, or perform IPC.

The current slice keeps only the reviewed empty-runtime bootstrap fallback
needed before the first immutable instance can own a Supervisor. It does not
claim the final v0.3 zero-main-thread-I/O instrumentation or real Desktop tool
injection acceptance.
