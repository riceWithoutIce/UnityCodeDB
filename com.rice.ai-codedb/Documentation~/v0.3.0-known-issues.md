# v0.3.0 Known Issues

This file records deferred issues that are intentionally separate from the
current implementation route. An entry here is not a release claim or a
GitProject status update.

## P2-001: Cold-start status briefly exposes recovery during convergence

- **Observed:** After a cold Unity start, the Manager can display
  `Starting -> Needs attention -> Starting -> Ready`.
- **Date recorded:** 2026-08-25.
- **Severity:** P2.
- **Current result:** The project eventually reaches `Ready`; immediate Play
  entry succeeds. No Host/config corruption or external-process termination
  was observed during the report.
- **User impact:** The transient `Needs attention` state exposes the
  `Reinstall CodeDB` action while automatic availability recovery is still in
  progress. A user could start an unnecessary second deployment or create a
  lifecycle race.
- **Working hypothesis:** A temporary current-instance/MCP availability
  failure is published through the lifecycle cache before the Manager's
  bounded transient-recovery presentation logic can normalize it back to
  `Starting`. The exact first failure reason (Provider, coordinator, or MCP
  startup window) still requires a timestamped Unity log capture.
- **Disposition:** Defer to the next status-reducer/Manager lifecycle task;
  do not make a standalone hotfix in the current snapshot.
- **Tracking:** Consolidated into the broader P2-002 lifecycle readiness and
  automatic-refresh controls UX task below.
- **Required closure:**
  1. A recoverable sequence remains `Starting` and does not expose
     `Reinstall CodeDB` until bounded recovery is exhausted.
  2. A persistent, non-recoverable failure still becomes `Needs attention`.
  3. `Missing prerequisite` remains distinct and is never normalized to
     `Starting`.
  4. A verified `Ready` observation is not cleared by one transient failed
     check.
  5. Add a direct regression for
     `Starting -> transient failure -> Starting -> Ready` and for the
     exhausted-failure path.
- **Escalation:** Raise to P1 if the intermediate state is persistent,
  repeatedly appears on every cold start for a user-visible interval, or
  causes normal users to invoke Reinstall before the automatic path reaches
  `Ready`.

## P2-002: Lifecycle readiness and automatic-refresh controls UX

- **Scope:** Consolidate the cold-start status presentation recorded in P2-001
  with the contextual manual watcher controls on the Index page.
- **Observed:** On a cold Unity start, the first Manager view can correctly
  show `Starting` while the background lifecycle pass is still preparing the
  project. Separately, when Automatic refresh is already `Enabled / Ready`,
  the Index page still presents `Start now`, `Stop now`, and `Restart` with
  equal prominence.
- **Severity:** P2.
- **Current result:** The background lifecycle remains automatic and eventually
  reaches `Ready`; no manual Manager action is required. The watcher commands
  are safe but their current labels and visibility do not explain whether they
  change persistent policy or only the current Unity session.
- **User impact:** Users may wait for a state that looks unfinished, believe
  they must open Manager to start CodeDB, click `Start now` while it is already
  running, or use `Stop now` without understanding that the startup policy is
  separate.
- **Disposition:** Defer as one focused status-reducer/Manager UX task. Do not
  change the asynchronous lifecycle or process-ownership contract in this
  snapshot.
- **Required closure:**
  1. Keep the automatic background preparation path independent of whether the
     Manager has been opened.
  2. Present `Starting` with a concise user-facing explanation and bounded
     preparation feedback; keep `Missing prerequisite` and `Needs attention`
     distinct.
  3. Keep recoverable startup windows from exposing `Reinstall CodeDB` before
     bounded recovery is exhausted.
  4. Derive the Index controls from watcher state: do not show `Start now` for
     an already running watcher, and show an explicit in-progress state while
     a command is executing.
  5. Distinguish persistent policies (`Start with Unity Editor` and
     `Automatic host updates`) from current-session actions such as
     `Start for this session`, `Stop for this session`, and `Restart`.
  6. Keep healthy-state manual controls secondary to `Refresh if stale`, while
     retaining a single contextual recovery action for stopped or failed
     states.
  7. Add focused regressions for cold startup with the Manager unopened/opened,
     transient recovery, missing prerequisites, and each watcher state/action
     combination; verify no duplicate backend start or external-process stop.
