# UnityCodeDB v0.2.2 Roadmap

Status: implementation complete; live Unity acceptance pending after
third-party v0.2.1 acceptance found release-blocking Windows query and upgrade
defects.

## Summary

The v0.2.1 Editor-owned lifecycle behaved reliably across automatic startup,
Pause and Resume, Domain Reload, Play Mode, normal shutdown, cold restart, and
forced Editor termination. The same acceptance found that a Ready coordinator
could still be unusable through the project MCP wrapper, and that an existing
generated Provider config could survive a package upgrade without newly
required fields.

v0.2.2 is a bounded patch release. It keeps the Editor-owned lifecycle and
Discover Read surface unchanged while making coordinator attachment,
project-runtime upgrades, Manager update state, and the window title bar
truthful on supported Windows configurations.

## Confirmed Findings

1. The wrapper treats every `process.kill(pid, 0)` error as a dead process.
   Windows `EPERM` across elevation boundaries therefore becomes a false
   `EDITOR_OFFLINE` or stopped-coordinator result.
2. A non-elevated acceptance also observed a Ready coordinator whose named
   pipe query returned a generic `STARTING` response. The current wrapper
   discards the socket error, so the cause is not yet proven.
3. The current Provider template contains `logging.flush_interval_ms`, but the
   runtime preparation command accepts an existing generated config without
   validating it. Upgrade must validate or explicitly regenerate that config;
   payload Sync must not silently overwrite generated runtime state.
4. A stale installed host payload is rendered through the generic warning
   label `Needs Setup` instead of the contracted `UPDATE_REQUIRED` state.
5. Sync guidance does not make active host-use lease blockers visible enough
   before a mutation attempt.
6. The EditorWindow tab icon is visually oversized and the tab title does not
   identify the installed package version.

## Decisions

- Coordinator-owned authenticated state and a successful pipe connection are
  authoritative for a Ready attachment. Wrapper probes must not independently
  override that truth solely because a permission-sensitive PID check fails.
- `EPERM` is indeterminate, not proof of death. Real stale state and PID reuse
  must still fail closed through process-start identity or coordinator-owned
  validation.
- Pipe diagnostics remain bounded and omit authentication material. A Ready
  state that cannot be contacted reports an explicit coordinator-unreachable
  result instead of an unexplained `STARTING` result.
- Existing runtime configs are validated before being called ready. Required
  upgrade is explicit and controlled; package payload materialization keeps its
  existing ownership boundary.
- `SETUP_REQUIRED`, `UPDATE_REQUIRED`, conflict, and blocked mutation states are
  separate user-facing outcomes.
- The EditorWindow uses a dedicated padded tab icon. The content header and
  documentation continue to use the existing brand asset.
- The title is `Codedb Manager vX.Y.Z`, sourced from Unity Package Manager
  metadata with a versionless fallback while metadata is unavailable.

## Scope

### Windows Query Reliability

1. Make wrapper process probes distinguish missing, alive, and indeterminate.
2. Prevent cross-elevation `EPERM` from invalidating live Editor demand or a
   live coordinator attachment.
3. Preserve zero Provider attempts for disabled, offline, stale, and
   unreachable states. Do not restore one-shot Provider fallback.
4. Preserve the named-pipe error code and state age in bounded diagnostics.
5. Add fixture coverage for permission-denied probes, Ready pipe success,
   Ready pipe failure, and real stale processes.

### Runtime Upgrade

1. Validate an existing formal Provider config before reporting it ready.
2. Identify missing required fields such as
   `logging.flush_interval_ms` as an upgrade requirement.
3. Provide an explicit regeneration path that retains the current runtime
   ownership and authorization boundaries.
4. Cover upgrades from older generated configs without making payload Sync
   overwrite ignored runtime files.

### Manager Truth And UI

1. Render stale installed payload as Update Required and never-installed
   payload as Setup Required.
2. Expose active host-use blockers in the pre-mutation guidance.
3. Use a dedicated tab icon with a smaller visual footprint.
4. Append the installed package version to the EditorWindow title and tooltip.

### Release Integrity

1. Advance package version, payload version and sequence, manifest hashes,
   changelog, and documentation together.
2. Re-run package boundary, materializer, Node and PowerShell syntax, payload
   hash, Unity EditMode, and diff checks.
3. Repeat live normal/elevated query, Play Mode, crash recovery, BatchMode, and
   two-project isolation acceptance before stable promotion.

## Acceptance

1. Normal Unity plus normal MCP and elevated Unity plus normal MCP can query a
   Ready coordinator without false `EDITOR_OFFLINE` or `STARTING` results.
2. Real dead or reused PIDs remain rejected and stale leases are reclaimed.
3. Ready pipe failures expose a bounded diagnostic without credentials and do
   not launch a Provider.
4. Existing incompatible runtime config is detected before Start and can be
   explicitly regenerated into a valid config.
5. Stale installed payload reports `UPDATE_REQUIRED`; missing payload reports
   `SETUP_REQUIRED`; Manager observation remains read-only.
6. Disabled and Editor-offline queries return their stable reason with
   `provider_attempts: 0`.
7. The tab title reports the installed package version and the padded icon is
   visually accepted in floating, docked, and narrow layouts.
8. The v0.2.1 lifecycle acceptance remains green.

## Validation Snapshot

Completed on 2026-07-28:

- All payload `.mjs` files pass `node --check`, and all modified PowerShell
  entry points pass the Windows PowerShell parser.
- The standalone package boundary passes, including payload hashes and the
  independent 48 x 48 tab-icon asset and GUID checks.
- The complete host-payload materializer fixture passes outside the restricted
  process sandbox. It covers runtime-config upgrade detection, explicit
  regeneration, read-only DryRun lease guidance, unreachable Ready pipes,
  permission-denied PID probes, lifecycle ownership, authorization, recovery,
  Sync, and Remove.
- The current Editor and EditMode test source assemblies compile with Unity
  2022.3.20f1's Roslyn compiler, generated defines, and reference set.

The Roslyn result is compile evidence only. Unity EditMode tests did not run:
the isolated BatchMode project exited with Unity Licensing code 199 before
project initialization and produced no test XML. Live normal/elevated query,
floating/docked/narrow visual acceptance, and two-project isolation therefore
remain release acceptance items.

## Environment-Blocked Retest Items

- BatchMode must reach project initialization before its no-lease behavior can
  be called a live pass; Unity Licensing exit 199 is not sufficient evidence.
- Two independently configured real Unity projects must run concurrently.
- A restricted environment `spawn EPERM` during the standalone fixture is not
  classified as a package defect until reproduced outside that environment.

## Out Of Scope

- New navigation tools or expansion beyond bounded Discover Read.
- A global CodeDB daemon or automatic Provider acquisition.
- Moving or rewriting the published v0.2.1 tag.
- Deleting unrelated legacy runtime directories in consuming projects.
