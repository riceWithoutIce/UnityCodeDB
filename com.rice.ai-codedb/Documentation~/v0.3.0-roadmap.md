# UnityCodeDB v0.3.0 Roadmap

Status: approved direction; starts from the selected instance/control contract
carried forward from the current v0.2.5 development snapshot. A published or
accepted v0.2.5 release is not a prerequisite. Deferred live lifecycle and
Discover Read validation are not treated as passed evidence.

Development and validation execution follows the project
[development workflow](development-workflow.md). For this roadmap, focused
verification is limited to L0 and directly affected L1 unless an explicit
acceptance task authorizes a broader gate.

## Release-Line Support Policy

The `v0.2.x` tags and published artifacts are historical and immutable. They
will not receive lifecycle, Domain Reload, Play-transition, or other runtime
maintenance fixes, and no `v0.2.4.x` hotfix line is planned. Compatibility
observation for those artifacts is limited to read-only inspection and bounded
query validation; that observation does not promote an old artifact to current
support or imply that its historical lifecycle behavior is corrected.

`v0.3.0` is the only active development and remediation line. Runtime
isolation, cold-start/Play responsiveness, and lifecycle correctness findings
are fixed and released only through the v0.3 Bridge/Supervisor route. Evidence
from a `v0.2.x` artifact may explain historical behavior, but cannot close a
v0.3 release gate. A v0.3 release requires fresh validation of a fixed package
artifact, including the main-thread runtime-isolation gates below.

## Summary

`v0.3.0` has a project-tool availability blocker and a control-plane migration
gate followed by two ordered workstreams. The P0 blocker must close
project-local Codex MCP discovery for a trusted standalone Unity project without
global registration. The separately approved control-contract migration defines
the explicit Reinstall boundary for incompatible runtime state. Runtime
isolation then makes Unity a thin lifecycle/UI Bridge over a project-local
external Supervisor. Bounded Discover Read expands on that stable runtime. The
query work cannot be considered complete while Editor callbacks still own
heavyweight runtime maintenance.

The current project wrapper exposes only status, find, search, text-search,
context, and bounded read. That is enough for limited discovery, but not for
reliable symbol navigation, dependency tracing, overloaded caller analysis,
Unity package source inspection, or a normal workflow that no longer uses `rg`
for routine indexed-code work.

Decision: retain the reviewed immutable payload, instance closure, and Package
handoff safety boundaries, but do not treat the current control namespace as a
release boundary. The separately approved [P0 control contract migration and
explicit Reinstall task](v0.3.0-p0-control-contract-migration.md) defines the
versioned control namespace, compatibility classification, atomic handoff, and
one-action recovery path. Each carried-forward contract must still pass the
v0.3.0 runtime gates; the snapshot is not release evidence. Then expand the
project-owned wrapper into a bounded Discover Read surface with explicit
freshness and strict output limits. The Supervisor remains project-local,
never machine-global.

## Selected Instance/Control Contract

`v0.3.0` adopts these reviewed contracts as implementation inputs. Their
selection does not promote the unpublished `v0.2.5` snapshot to a release:

- `control/desired-state.json`, `current-instance.json`,
  `last-known-good-instance.json`, and `operation.json`;
- immutable `host/generations/<generation-id>/` and isolated
  `instances/<instance-id>/` layouts;
- candidate provision, initialize/tools/status/query verification, atomic
  activation, rollback, and asynchronous retired-instance cleanup;
- side-by-side first install, Package upgrade, Reinstall, and logical Uninstall;
- one serialized project operation, cached Manager progress, and bounded
  cold-start/immediate-Play behavior.

The v0.3 runtime line must not reintroduce in-place Repair or make old-instance
cleanup a prerequisite for selecting a verified new instance.

## P0 Package Runtime Version Contract And Routing

The current snapshot manually repeats the target generation identity across C#,
PowerShell, Node.js, the stable wrapper, Package pointers, and payload manifests.
That duplication produced a demonstrated correctness defect: the Editor could
classify an exact Package-declared previous instance, while a downstream
deployment validator still admitted only the current generation. The resulting
fail-closed refusal protected project bytes, but broke the normal automatic
handoff path. This is a v0.3 foundation defect, not a reason to weaken immutable
instance authentication or accept arbitrary historical generations.

The bounded current-generation/previous-generation repair remains a migration
checkpoint, not the final architecture. Do not add more caller-controlled
`AllowPreviousGeneration`-style bypasses. A previous instance must be classified
and authenticated completely before any candidate activation or other related
mutation; downstream callers must not be required to remember a second,
stronger validation step.

### Authority And Dependency Direction

1. `Payload~/payload-manifest.json` is the only manually maintained Package
   runtime-version contract. Its current identity, bootstrap protocol, exact
   transition allowlist, and immutable closure hashes are authoritative.
2. The project Supervisor/materializer owns selected-instance integrity,
   version classification, transition planning, activation, rollback, and
   retirement decisions. Multiple bootstrap implementations may strictly parse
   the versioned contract, but they must not carry independent version policy.
3. The stable project wrapper is a version-neutral router. It resolves the
   atomically selected `current-instance.json`, validates project identity,
   path and reparse boundaries, instance-manifest hash, worker path, and worker
   hash, then pins that instance for the connection and publishes its lease. It
   must not contain an independently maintained expected generation.
4. The Unity Bridge consumes only bounded authenticated Supervisor state and
   enqueues lifecycle intent. It does not classify current/previous generations,
   scan Package or project generation directories, hash closures, or perform
   version-policy filesystem work on the Unity main thread.
5. Manager renders the cached classification and operation progress. Opening or
   repainting Manager never becomes a version-reconciliation trigger.

The runtime status schema keeps these identities distinct:

- `target_generation_id`: the current Package target;
- `selected_generation_id`: the atomically selected project instance;
- `runtime_contract_sha256`: the exact Package contract snapshot used for the
  decision;
- `supervisor_protocol_version`: the compatibility boundary for Bridge IPC.

The authoritative disposition is one of `CURRENT`, `TRUSTED_PREVIOUS`, `NEWER`,
`SEQUENCE_COLLISION`, or `INVALID`. `TRUSTED_PREVIOUS` requires one exact
Package-declared transition and the preserved Package-owned immutable byte
closure. Each transition also binds the exact Package-owned stable-wrapper
SHA-256 that may accompany that source instance; a previous instance never
authorizes the current wrapper or an arbitrary historical launcher. New
candidates remain current-target-only. Previous instances are admitted only
for retention, handoff, rollback, and lease-aware retirement.
Newer identities, same-sequence identity collisions, undeclared generations,
path escapes, reparse points, missing files, and hash drift remain fail-closed.

An already connected MCP client stays pinned to its selected immutable instance;
it does not follow a later pointer change. New connections resolve the newly
activated instance. Cleanup never terminates an external MCP client and waits
for the corresponding instance lease to drain.

### Priority Migration Boundary

This P0 includes the shared contract model, one disposition model, structured
Supervisor classification, version-neutral stable-wrapper routing, removal of
manual generation decisions from Unity/PowerShell/Node runtime control paths,
and migration of Bridge/Manager to cached Supervisor results. Schema and
protocol constants, ownership labels, strict path rules, immutable generation
directory names, generated artifacts, and explicit test fixtures may retain
their required identities.

This P0 does not redesign the selected instance/control layout, activation
journal, rollback, lease format, Provider/index/query queue, Manager visual
design, or immutable generation contents. It does not backport lifecycle fixes
to v0.2.x or expand into the later Discover Read feature set.

### Acceptance

1. A synthetic contract-only `poc.34` to `poc.35` bump, with `poc.34` declared
   as the exact source transition, completes classification, candidate
   verification, atomic activation, and routing without manually updating a
   current-generation constant in C#, PowerShell, or Node.js control logic.
2. Every declared transition is exercised through the Editor-facing cached
   result, deployment planner, activation, rollback selection, and retirement
   classifier. Current, previous, newer, same-sequence collision, undeclared,
   tampered-closure, and tampered stable-wrapper cases have deterministic
   results before candidate publication.
3. An active previous MCP remains alive and byte-pinned while a new connection
   selects the current instance; cleanup converges only after natural lease
   drain.
4. Project-writable selection evidence cannot authorize an arbitrary worker:
   project identity, reviewed roots, no-reparse boundaries, instance-manifest
   hash, worker path, and worker hash are all verified before launch.
5. A source audit finds no manually maintained current-generation decision in
   runtime control paths outside the authoritative contract or generated/test
   artifacts.
6. Fresh Unity evidence confirms that classification and routing introduce no
   filesystem, hash, process, lock, PowerShell/Node, or synchronous IPC work on
   the Unity main thread.

The Package currently proves project TOML validity and direct wrapper/backend
availability, while a real new Codex task in the standalone non-Git acceptance
project exposes no project tool namespace. Configuration readiness, Package
backend readiness, and actual Codex client observation must remain distinct.

The frozen investigation, UI semantics, safety boundaries, focused validation,

This blocker must not be bypassed with user-global CodeDB registration, a fake

real client acceptance.

## Runtime Isolation Scope

1. Keep Unity's main-thread Bridge limited to lifecycle signals, resolved
   Package identity, UI rendering, confirmation, and in-memory event enqueue.
2. Connect through versioned asynchronous IPC to one project-local external
   Supervisor. Reconnect after Domain Reload without restarting a healthy
   backend.
3. Move status evaluation, indexing, refresh, cleanup, Provider/adapter work,
   and process lifecycle into a query-first queue with one heavy job at a time.
4. Expose stable `CORE_READY`, `STARTING`, `MAINTENANCE`, `DEGRADED`, `BLOCKED`,
   `STOPPING`, and `STOPPED` states. A valid stale index remains queryable; a
   missing index reports bounded startup instead of blocking Unity.
5. Treat compilation, asset updates, and Play transitions as scheduling inputs,
   not synchronous work. Final Editor exit stops only authenticated
   project-owned backends and never an external MCP client.
6. Make Manager a cached Supervisor client. Opening or repainting it performs no
   filesystem scan, process launch, hash, lock wait, or synchronous IPC.

Runtime acceptance requires Domain Reload reconnect, queue ordering,
stale/missing-index behavior, outage/fallback behavior, final shutdown ownership,
and instrumentation showing zero CodeDB filesystem, hash, process, lock,
synchronous IPC, or full-status work on Unity's main thread. The basic Package
handoff and cold-Play foundations are carried forward from the selected
instance/control contract; the stronger Supervisor and zero-I/O claims require
new v0.3 evidence.

## P0 Supervisor Runtime Ownership And Crash Recovery

This P0 was opened for a release-blocking recovery gap independent of generation
routing: state and lock files could outlive their process, the Bridge could
attempt a stale pipe without a safe takeover, and child ownership did not share
one complete process identity. The current source snapshot implements the
resulting ownership, publication, takeover, and operation-recovery contract.
It remains an implementation snapshot rather than release acceptance until the
fresh Unity and external-client gates below are actually executed.

This is one ownership/recovery problem, not a new `poc`-specific repair path. It
is tracked in the [P0 Supervisor runtime ownership and crash recovery task](v0.3.0-p0-supervisor-runtime-recovery.md).

The task establishes the following contract:

1. Runtime evidence is classified as `MISSING`, `STARTING_OWNED`,
   `LIVE_AUTHENTICATED`, `STALE_PROVED`, or `INVALID_OR_AMBIGUOUS`. File
   existence, PID existence, or a recent timestamp is never sufficient by
   itself.
2. Supervisor, Coordinator, and every Package-owned child bind their PID to a
   process-start identity, exact executable/argv identity, project/runtime
   identity, owner epoch, and the independently authenticated pipe where
   applicable. An unavailable identity remains ambiguous and fail-closed.
3. Ownership is hierarchical: the Unity Bridge classifies and contacts only
   the Supervisor; the Supervisor owns Coordinator admission and operation
   recovery; the Coordinator owns Provider and adapter children. Peer layers do
   not independently guess that another owner is stale.
4. State publication is strict UTF-8, flushed temporary-file plus atomic
   replacement with bounded retry. Replacement never uses delete-then-move, and
   readers use sharing semantics compatible with replacement-only publication.
5. A stale takeover uses an atomic claim/recheck. It may remove or quarantine
   old control evidence only after stale ownership and the absence of a live
   admitted child operation are proved. Invalid or ambiguous evidence is not
   silently treated as missing.
6. Admitted operations persist enough child identity and result evidence to be
   reattached, waited on, or verified from the materializer transaction journal
   after a Supervisor crash. A reconnect cannot launch a duplicate operation.
7. One-shot fallback is allowed only for a proven bootstrap/missing-owner case,
   never for an unclassified transport timeout. Automatic retries are bounded
   by an evidence epoch and do not repeatedly submit the same failed
   Upgrade/Probe operation.
8. External MCP clients and unrelated processes remain outside every takeover,
   stop, and cleanup path. Only independently authenticated Package-owned
   processes may be stopped.

This gate does not redesign the selected instance/control layout, replace the
Provider, add a global daemon, or backport lifecycle fixes to `v0.2.x`. It also
does not mutate a published immutable generation in place. If a Coordinator
byte change is required, it must be packaged under the normal immutable
generation transition rule; a new generation is not a substitute for closing
the ownership contract.

The selected control layout is now a separately approved migration boundary.
The [P0 control contract migration and explicit Reinstall task](v0.3.0-p0-control-contract-migration.md)
defines the required versioned namespace and handoff before this runtime is
treated as a release boundary.

## Product Contract

- All new tools remain project-level, read-only, and bounded.
- Project source and approved dependency source are reported as separate lanes.
- A result is never silently treated as complete when freshness, support,
  truncation, or symbol identity is uncertain.
- Ambiguous symbol navigation requires a definition path and line anchor.
- One MCP response remains capped at 64 KiB.
- A batch contains at most 10 read-only operations and obeys one aggregate
  output budget.
- `rg` remains the verification and explicit fallback baseline until every
  release gate passes.

## Scope

### Bounded Navigation Surface

1. Add bounded tree/list and glob operations for indexed paths.
2. Add symbol definition and file outline operations.
3. Add callers/references with `definition_path` and `definition_line`
   anchoring for overload and same-name disambiguation.
4. Add direct and bounded transitive dependency/include traversal.
5. Add a budgeted explore operation that composes ranked files, outlines,
   dependency hints, and focused source excerpts.
6. Keep broad graph export, shell, edit, remote, memory, and cross-project tools
   unavailable from the default profile.

### Context And Batch

1. Replace text-search-only context with candidates informed by symbols,
   dependencies, and semantic ranking.
2. Preserve explicit evidence explaining why each returned file is relevant.
3. Add a maximum 10-operation read-only batch with a 64 KiB aggregate response
   ceiling and per-operation error reporting.
4. Do not add implicit batching or hide individual tool failures.

### Freshness And Language Lanes

1. Guarantee query-time Shader/HLSL freshness or return `STALE` before serving
   an incomplete result.
2. Expose incremental adapter state, last successful update, source snapshot,
   changed-file counts, and rebuild reason.
3. Keep C# Provider and Shader/HLSL adapter results distinct before the wrapper
   performs bounded merge and deduplication.
4. Preserve rename, delete, line-ending, and transient-write diagnostics.

### Controlled Unity Dependency Lane

1. Resolve only packages pinned by the Unity project manifest and lock file.
2. Index approved package source in a separate version-keyed dependency lane.
3. Label every result as project source or dependency source.
4. Refresh dependency data only when the resolved package identity changes.
5. Keep arbitrary `Library/PackageCache` scanning, unrelated cached versions,
   and machine-wide package discovery out of scope.

### Explicit Result Semantics

Every unavailable or incomplete operation returns a stable reason such as:

- `STALE`;
- `UNSUPPORTED`;
- `TRUNCATED`;
- `AMBIGUOUS`;
- `OUT_OF_SCOPE`;
- `INVALID_ARGUMENT`.

A legitimate zero-hit result remains distinguishable from these conditions.

## Acceptance Corpus

Build at least 50 real project queries covering:

- exact text and regex;
- file name, list, and glob;
- symbol definition and file outline;
- overloaded and same-name callers;
- imports, dependencies, and Shader includes;
- C#, Shader, HLSL, CGINC, and Compute source;
- created, modified, renamed, and deleted files;
- project source versus controlled Unity dependency source.

## Runtime Release Gates

1. The Bridge and Manager perform no CodeDB filesystem, hash, process, lock,
   synchronous IPC, PowerShell/Node, indexing, or full-status work on Unity's
   main thread; instrumentation verifies the claim.
2. Domain Reload reconnects to the same healthy Supervisor and selected instance
   without duplicate backend startup.
3. Query-first scheduling preserves available queries during maintenance; heavy
   work serializes and defers across compile, asset update, and Play transitions.
4. A valid stale index remains queryable with explicit freshness. A missing
   index reports bounded `STARTING`/`CORE_READY` and builds in the background.
5. Supervisor outage remains fail-closed and never authorizes a second command
   owner. One-shot materializer fallback is limited to a proven empty-runtime
   bootstrap. Final shutdown stops authenticated project backends only and
   preserves every external MCP client.
6. Fresh local Unity and third-party Package-only acceptance cover the exact
   v0.3 preview. Unexecuted two-project/elevation matrices remain `DEFERRED`.

## Discover Read Release Gates

1. Exact text, file, and regex result completeness is 100% against the `rg`
   baseline for the acceptance corpus.
2. Modified indexed code is returned inside the declared freshness window, or
   the operation returns `STALE`; silent stale misses are release-blocking.
3. Anchored caller and dependency samples have no cross-symbol merge errors.
4. Every result remains inside the canonical Unity project or an explicitly
   approved dependency lane.
5. Common internal query p95 is at most 200 ms on the representative Unity
   corpus; multi-step navigation uses bounded batch to limit MCP round trips.
6. Context results include meaningful symbol/dependency/semantic evidence and
   outperform text-search-only context on the reviewed natural-language set.
7. Ten consecutive real code navigation or analysis tasks complete without
   routine `rg`, and independent baseline verification agrees with the result.
8. Only after all gates pass may the normal workflow prefer project CodeDB and
   permit `rg` solely for explicit fallback reasons.

## Out Of Scope

- Write, edit, shell, remote execution, memory mutation, or cross-project tools.
- Broad source or graph export bundles.
- Indexing every package cached on the machine.
- A global CodeDB service replacing project-owned wrappers.
- Redesigning the v0.2.5 payload contents, Provider, or Package handoff safety
  boundaries. The separately approved v0.3 control-contract migration may
  change the control namespace and activation handoff only within its task
  contract.
- Removing `rg` before the acceptance corpus and workflow trial pass.
