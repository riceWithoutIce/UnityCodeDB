# UnityCodeDB v0.3.0 Roadmap

Status: approved direction; starts after stable v0.2.4 promotion. Deferred live
lifecycle validation remains tracked in the v0.2.5 roadmap and is not treated
as passed evidence.

## Summary

Problem: the project wrapper currently exposes only status, find, search,
text-search, context, and bounded read. That is enough for limited discovery,
but not for reliable symbol navigation, dependency tracing, overloaded caller
analysis, Unity package source inspection, or a normal workflow that no longer
uses `rg` for routine indexed-code work. Availability also does not guarantee
adoption: a source-dependent implementation, diagnosis, documentation, or
architecture task can skip a Ready CodeDB unless the client has an explicit
task-level invocation policy.

Decision: expand the existing project-owned wrapper into a bounded Discover
Read surface while preserving the v0.2.2 corrected Editor-owned lifecycle,
project-local runtime, explicit freshness, and strict output limits. Do not
replace it with a global full-service CodeDB instance. Define a separate
task-aware invocation contract for managed client integrations. Automatic
refresh keeps indexes current; it does not imply that an MCP client will query
CodeDB for a task.

## Trigger Decision Record

On 2026-08-05, a Balance architecture review started with local source reads
and Git history without calling CodeDB. A later read-only check reported the
`0.2.5-preview.2` wrapper and `poc.29` generation Ready, automatic refresh
active, and targeted `GameManager` plus `Main` search/read results consistent
with the local files. No index refresh or project mutation was needed.

The evidence classifies the missed initial call as an invocation-policy gap,
not a Provider, index, wrapper, or coverage failure. The Ready/active values are
timestamped runtime evidence rather than a permanent project guarantee, and
the focused file checks do not claim repository-wide completeness.

## Candidate Matrix

| Candidate | Capability | Project isolation | Operational cost | Decision |
| --- | --- | --- | --- | --- |
| Keep the six-tool wrapper and routine `rg` fallback | Limited search/read | Strong | Lowest | Keep only as the current baseline |
| Use a global complete CodeDB service | Broad | Violates project ownership and runtime isolation | Shared hidden state | Reject |
| Extend the project wrapper with bounded read-only navigation | Broad enough for normal analysis | Preserves project ownership | Moderate protocol and test work | Approve |

## Invocation Candidate Matrix

| Candidate | Adoption behavior | Cost and risk | Decision |
| --- | --- | --- | --- |
| Invoke CodeDB for every task | Maximum raw call frequency | Adds noise and latency to tasks with no source dependency | Reject |
| Leave invocation entirely to model discretion | Matches the current integration baseline | Ready CodeDB is skipped unpredictably | Reject as the normal workflow |
| Require a source-dependency decision for every project task | Uses CodeDB when current source can affect the answer and records explicit skips | Requires client-side routing and task-level telemetry | Approve |

## Product Contract

- All new tools remain project-level, read-only, and bounded.
- Project source and approved dependency source are reported as separate lanes.
- A result is never silently treated as complete when freshness, support,
  truncation, or symbol identity is uncertain.
- Ambiguous symbol navigation requires a definition path and line anchor.
- One MCP response remains capped at 64 KiB.
- A batch contains at most 10 read-only operations and obeys one aggregate
  output budget.
- `rg` remains the verification and explicit fallback baseline until every
  release gate passes.
- Automatic index refresh and automatic task invocation remain separate
  contracts. Reporting one as evidence for the other is invalid.
- The decision unit is a user task, not an individual tool call and not the
  coding/non-coding label. A documentation or architecture task can still be
  source-dependent.
- Every project task receives an explicit source-dependency decision. A skipped
  CodeDB path carries a stable reason instead of remaining invisible.
- A status-only call does not satisfy a source-dependent task. Successful
  preflight must be followed by targeted search, navigation, or bounded read
  evidence before the client relies on CodeDB.

## Scope

### Task-Aware Invocation

1. Classify each project task by whether current indexed source can materially
   affect the answer or planned mutation.
2. Require a Ready/status preflight and targeted CodeDB evidence for
   implementation, diagnosis, code review, architecture review, code-backed
   documentation, and dependency or Shader/HLSL analysis.
3. Treat release, Git, asset, scene, configuration, and planning tasks as
   conditional: invoke CodeDB when implementation evidence matters, otherwise
   record the skip.
4. Skip pure rewriting, translation, general conversation, and other tasks
   with no project-source dependency.
5. Record stable skip or fallback reasons such as `NOT_SOURCE_DEPENDENT`,
   `USER_EXCLUDED`, `UNAVAILABLE`, and `OUT_OF_SCOPE`. Unavailable CodeDB is a
   fallback condition, never a zero-hit result.
6. Keep task classification and skip telemetry in the managed client
   integration. The package and wrapper do not infer user intent or launch
   autonomous queries.
7. Keep local source and Git reads as explicit verification or fallback. They
   do not silently replace the required CodeDB decision.

Measure invocation behavior at task level:

- decision coverage: tasks with an explicit use/skip decision;
- required invocation coverage: source-dependent tasks that actually query
  CodeDB, excluding reviewed unavailable or user-excluded cases;
- evidence-use rate: successful queries whose results influence the answer or
  are explicitly reported as irrelevant or zero-hit;
- skip precision: skipped tasks that genuinely did not require indexed source.

### Bounded Navigation Surface

1. Add bounded tree/list and glob operations for indexed paths.
2. Add symbol definition and file outline operations.
3. Add callers/references with `definition_path` and `definition_line`
   anchoring for overload and same-name disambiguation.
4. Add direct and bounded transitive dependency/include traversal.
5. Add a budgeted explore operation that composes ranked files, outlines,
   dependency hints, and focused source excerpts.
6. Keep broad graph export, shell, edit, remote, memory, and cross-project tools
   unavailable from the default profile.

### Context And Batch

1. Replace text-search-only context with candidates informed by symbols,
   dependencies, and semantic ranking.
2. Preserve explicit evidence explaining why each returned file is relevant.
3. Add a maximum 10-operation read-only batch with a 64 KiB aggregate response
   ceiling and per-operation error reporting.
4. Do not add implicit batching or hide individual tool failures.

### Freshness And Language Lanes

1. Guarantee query-time Shader/HLSL freshness or return `STALE` before serving
   an incomplete result.
2. Expose incremental adapter state, last successful update, source snapshot,
   changed-file counts, and rebuild reason.
3. Keep C# Provider and Shader/HLSL adapter results distinct before the wrapper
   performs bounded merge and deduplication.
4. Preserve rename, delete, line-ending, and transient-write diagnostics.

### Controlled Unity Dependency Lane

1. Resolve only packages pinned by the Unity project manifest and lock file.
2. Index approved package source in a separate version-keyed dependency lane.
3. Label every result as project source or dependency source.
4. Refresh dependency data only when the resolved package identity changes.
5. Keep arbitrary `Library/PackageCache` scanning, unrelated cached versions,
   and machine-wide package discovery out of scope.

### Explicit Result Semantics

Every unavailable or incomplete operation returns a stable reason such as:

- `STALE`;
- `UNSUPPORTED`;
- `TRUNCATED`;
- `AMBIGUOUS`;
- `OUT_OF_SCOPE`;
- `INVALID_ARGUMENT`.

A legitimate zero-hit result remains distinguishable from these conditions.

## Acceptance Corpus

Build a reviewed task-trigger corpus spanning:

- implementation, debugging, refactoring, review, and architecture work;
- code-backed documentation, planning, and release communication;
- Unity assets, scenes, configuration, packages, and Shader/HLSL work;
- repository-only operations and pure non-source writing tasks;
- Ready, stale, unavailable, out-of-scope, and user-excluded CodeDB states.

The corpus must include both coding and non-coding tasks. Labels alone are not
accepted as the source-dependency decision.

Separately, build at least 50 real project queries covering:

- exact text and regex;
- file name, list, and glob;
- symbol definition and file outline;
- overloaded and same-name callers;
- imports, dependencies, and Shader includes;
- C#, Shader, HLSL, CGINC, and Compute source;
- created, modified, renamed, and deleted files;
- project source versus controlled Unity dependency source.

## Release Gates

1. Every task in the trigger corpus has an explicit, reviewable use or skip
   decision.
2. Every source-dependent corpus task invokes CodeDB without an explicit user
   reminder, or records a reviewed unavailable or user-excluded fallback.
3. A successful CodeDB invocation contributes evidence to the result, or the
   client explicitly records that the result was irrelevant or a legitimate
   zero-hit.
4. Exact text, file, and regex result completeness is 100% against the `rg`
   baseline for the acceptance corpus.
5. Modified indexed code is returned inside the declared freshness window, or
   the operation returns `STALE`; silent stale misses are release-blocking.
6. Anchored caller and dependency samples have no cross-symbol merge errors.
7. Every result remains inside the canonical Unity project or an explicitly
   approved dependency lane.
8. Common internal query p95 is at most 200 ms on the representative Unity
   corpus; multi-step navigation uses bounded batch to limit MCP round trips.
9. Context results include meaningful symbol/dependency/semantic evidence and
   outperform text-search-only context on the reviewed natural-language set.
10. Ten consecutive real code navigation or analysis tasks trigger CodeDB
   through the normal workflow without a user reminder, complete without
   routine `rg`, and agree with independent baseline verification.
11. Only after all gates pass may the normal workflow prefer project CodeDB and
   permit `rg` solely for explicit fallback reasons.

## Delivery Sequence

1. Freeze the task-trigger corpus, source-dependency taxonomy, stable skip
   reasons, and integration ownership boundary.
2. Freeze the query corpus and `rg` comparison harness.
3. Add managed client invocation policy and task-level decision telemetry
   without teaching the package to infer user intent.
4. Add list/glob, symbol, and outline with strict schemas and bounds.
5. Add anchored callers and dependency traversal.
6. Add budgeted explore and explicit result reason codes.
7. Add semantic context and the bounded 10-operation batch.
8. Add Shader/HLSL query-time freshness and incremental observability.
9. Add the controlled Unity dependency lane.
10. Run trigger, performance, completeness, ambiguity, isolation, and ten-task
    no-`rg` acceptance before changing the formal usage rule.

## Out Of Scope

- Write, edit, shell, remote execution, memory mutation, or cross-project tools.
- Broad source or graph export bundles.
- Indexing every package cached on the machine.
- A global CodeDB service replacing project-owned wrappers.
- Removing `rg` before the acceptance corpus and workflow trial pass.
- Blindly invoking CodeDB for tasks that have no project-source dependency.
- Treating automatic refresh, wrapper readiness, or tool exposure as proof that
  a client actually considered or used CodeDB for a task.
