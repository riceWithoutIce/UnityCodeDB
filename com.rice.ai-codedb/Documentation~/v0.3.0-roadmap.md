## Release-Line Support Policy

The `v0.2.x` tags and published artifacts are historical and immutable. They
will not receive lifecycle, Domain Reload, Play-transition, or other runtime
maintenance fixes, and no `v0.2.4.x` hotfix line is planned. Compatibility
observation for those artifacts is limited to read-only inspection and bounded
query validation; that observation does not promote an old artifact to current
support or imply that its historical lifecycle behavior is corrected.

`v0.3.0` is the only active development and remediation line. Runtime
isolation, cold-start/Play responsiveness, and lifecycle correctness findings
are fixed and released only through the v0.3 Bridge/Supervisor route. Evidence
from a `v0.2.x` artifact may explain historical behavior, but cannot close a
v0.3 release gate. A v0.3 release requires fresh validation of a fixed package
artifact, including the main-thread runtime-isolation gates below.

For incompatible preview integration state, the frozen recovery route is
[controlled project integration uninstall followed by fresh reinstall](v0.3.0-p0-project-integration-reinstall-contract.md).
It is distinct from removing the Unity Package; automatic cross-version
Package upgrades are deferred until the control/runtime contracts stabilize.

## Summary

`v0.3.0` has a project-tool availability gate and a preview integration
recovery gate followed by two ordered workstreams. The project-local Codex MCP
discovery gate still requires real new-task evidence. For incompatible preview
runtime state, the current P0 recovery contract is controlled project
integration uninstall, authenticated `Uninstalled`, then fresh install. It
does not require transparent cross-version Package upgrade. Runtime isolation
makes Unity a thin lifecycle/UI Bridge over a project-local external

Supervisor remains project-local, never machine-global.

## P0 Package Runtime Version Contract And Routing

The current snapshot manually repeats the target generation identity across C#,
PowerShell, Node.js, the stable wrapper, Package pointers, and payload manifests.
That duplication produced a demonstrated correctness defect: the Editor could
classify an exact Package-declared previous instance, while a downstream
deployment validator still admitted only the current generation. The resulting
fail-closed refusal protected project bytes, but broke the normal automatic
handoff path. This is a v0.3 foundation defect, not a reason to weaken immutable
instance authentication or accept arbitrary historical generations.

The bounded current-generation/previous-generation repair remains a migration
checkpoint, not the final architecture. Do not add more caller-controlled
`AllowPreviousGeneration`-style bypasses. A previous instance must be classified
and authenticated completely before any candidate activation or other related
mutation; downstream callers must not be required to remember a second,
stronger validation step.

### Authority And Dependency Direction

1. `Payload~/payload-manifest.json` is the only manually maintained Package
   runtime-version contract. Its current identity, bootstrap protocol, exact
   transition allowlist, and immutable closure hashes are authoritative.
2. The project Supervisor/materializer owns selected-instance integrity,
   version classification, transition planning, activation, rollback, and
   retirement decisions. Multiple bootstrap implementations may strictly parse
   the versioned contract, but they must not carry independent version policy.
3. The stable project wrapper is a version-neutral router. It resolves the
   atomically selected `current-instance.json`, validates project identity,
   path and reparse boundaries, instance-manifest hash, worker path, and worker
   hash, then pins that instance for the connection and publishes its lease. It
   must not contain an independently maintained expected generation.
4. The Unity Bridge consumes only bounded authenticated Supervisor state and
   enqueues lifecycle intent. It does not classify current/previous generations,
   scan Package or project generation directories, hash closures, or perform
   version-policy filesystem work on the Unity main thread.
5. Manager renders the cached classification and operation progress. Opening or
   repainting Manager never becomes a version-reconciliation trigger.

The runtime status schema keeps these identities distinct:

- `target_generation_id`: the current Package target;
- `selected_generation_id`: the atomically selected project instance;
- `runtime_contract_sha256`: the exact Package contract snapshot used for the
  decision;
- `supervisor_protocol_version`: the compatibility boundary for Bridge IPC.

The authoritative disposition is one of `CURRENT`, `TRUSTED_PREVIOUS`, `NEWER`,
`SEQUENCE_COLLISION`, or `INVALID`. `TRUSTED_PREVIOUS` requires one exact
Package-declared transition and the preserved Package-owned immutable byte
closure. Each transition also binds the exact Package-owned stable-wrapper
SHA-256 that may accompany that source instance; a previous instance never
authorizes the current wrapper or an arbitrary historical launcher. New
candidates remain current-target-only. Previous instances are admitted only
for retention, handoff, rollback, and lease-aware retirement.
Newer identities, same-sequence identity collisions, undeclared generations,
path escapes, reparse points, missing files, and hash drift remain fail-closed.

An already connected MCP client stays pinned to its selected immutable instance;
it does not follow a later pointer change. New connections resolve the newly
activated instance. Cleanup never terminates an external MCP client and waits
for the corresponding instance lease to drain.

### Priority Migration Boundary

This P0 includes the shared contract model, one disposition model, structured
Supervisor classification, version-neutral stable-wrapper routing, removal of
manual generation decisions from Unity/PowerShell/Node runtime control paths,
and migration of Bridge/Manager to cached Supervisor results. Schema and
protocol constants, ownership labels, strict path rules, immutable generation
directory names, generated artifacts, and explicit test fixtures may retain
their required identities.

This P0 does not redesign the selected instance/control layout, activation
journal, rollback, lease format, Provider/index/query queue, Manager visual
design, or immutable generation contents. It does not backport lifecycle fixes
to v0.2.x or expand into the later Discover Read feature set.

## P0 Supervisor Runtime Ownership And Crash Recovery

This P0 was opened for a release-blocking recovery gap independent of generation
routing: state and lock files could outlive their process, the Bridge could
attempt a stale pipe without a safe takeover, and child ownership did not share
one complete process identity. The current source snapshot implements the
resulting ownership, publication, takeover, and operation-recovery contract.
It remains an implementation snapshot rather than release acceptance until the
fresh Unity and external-client gates below are actually executed.

This is one ownership/recovery problem, not a new `poc`-specific repair path. It
is tracked in the [P0 Supervisor runtime ownership and crash recovery task](v0.3.0-p0-supervisor-runtime-recovery.md).

The task establishes the following contract:

1. Runtime evidence is classified as `MISSING`, `STARTING_OWNED`,
   `LIVE_AUTHENTICATED`, `STALE_PROVED`, or `INVALID_OR_AMBIGUOUS`. File
   existence, PID existence, or a recent timestamp is never sufficient by
   itself.
2. Supervisor, Coordinator, and every Package-owned child bind their PID to a
   process-start identity, exact executable/argv identity, project/runtime
   identity, owner epoch, and the independently authenticated pipe where
   applicable. An unavailable identity remains ambiguous and fail-closed.
3. Ownership is hierarchical: the Unity Bridge classifies and contacts only
   the Supervisor; the Supervisor owns Coordinator admission and operation
   recovery; the Coordinator owns Provider and adapter children. Peer layers do
   not independently guess that another owner is stale.
4. State publication is strict UTF-8, flushed temporary-file plus atomic
   replacement with bounded retry. Replacement never uses delete-then-move, and
   readers use sharing semantics compatible with replacement-only publication.
5. A stale takeover uses an atomic claim/recheck. It may remove or quarantine
   old control evidence only after stale ownership and the absence of a live
   admitted child operation are proved. Invalid or ambiguous evidence is not
   silently treated as missing.
6. Admitted operations persist enough child identity and result evidence to be
   reattached, waited on, or verified from the materializer transaction journal
   after a Supervisor crash. A reconnect cannot launch a duplicate operation.
7. One-shot fallback is allowed only for a proven bootstrap/missing-owner case,
   never for an unclassified transport timeout. Automatic retries are bounded
   by an evidence epoch and do not repeatedly submit the same failed
   Upgrade/Probe operation.
8. External MCP clients and unrelated processes remain outside every takeover,
   stop, and cleanup path. Only independently authenticated Package-owned
   processes may be stopped.

This gate does not redesign the selected instance/control layout, replace the
Provider, add a global daemon, or backport lifecycle fixes to `v0.2.x`. It also
does not mutate a published immutable generation in place. If a Coordinator
byte change is required, it must be packaged under the normal immutable
generation transition rule; a new generation is not a substitute for closing
the ownership contract.

The selected control layout remains a migration boundary. The historical
[P0 control contract migration design](v0.3.0-p0-control-contract-migration.md)
records the namespace and handoff foundations; the [preview recovery
contract](v0.3.0-p0-project-integration-reinstall-contract.md) now requires
authenticated project uninstall before fresh install. Neither design nor the
current local Package is release evidence.
