# v0.3.0 P0: Project-local Codex MCP Discovery

Status: frozen release blocker; implementation has not started.

Date frozen: 2026-08-26.

## Purpose

Close the gap between a Package-prepared project MCP configuration and the
tools that a real new Codex task receives. The Manager currently proves that
the project configuration is structurally valid and that the Package can start
and query its wrapper directly. Those facts do not prove that a Codex client
loaded the project configuration or exposed the project tool namespace.

This is a normal-user-path release blocker. A standalone Unity project must be
usable without a user-global CodeDB registration, a synthetic Git repository,
or manual Codex configuration changes.

## Confirmed Evidence

The current acceptance project is `G:\RiceProgram\Test\Test`.

- A real new Codex task reported that exact working directory.
- The project configuration contains an enabled `codedb-test` stdio server
  whose command, working directory, arguments, and timeout match the Package
  contract.
- The Package-owned availability probe successfully completed MCP initialize,
  exact `tools/list`, usable `codedb_status`, and one bounded
  `codedb_text_search` against the selected `poc.33` instance.
- The same real Codex task exposed no `mcp__codedb_test__*` tools.

Therefore the Provider, selected instance, and direct wrapper path are not the
current failing layer. Codex project discovery, client startup, or tool
injection remains unproven.

## External Contract

Official OpenAI documentation states that local Codex clients share MCP
configuration and that an MCP server can be scoped to a trusted project through
`.codex/config.toml`:

- <https://developers.openai.com/codex/mcp>

The documentation does not state that a project must contain a Git repository.
The acceptance project's lack of `.git` is therefore a high-priority diagnostic
hypothesis, not an accepted product restriction or a confirmed root cause.

## Frozen Product Contract

1. CodeDB remains project-local. It must not add or depend on a user-global
   CodeDB MCP registration.
2. CodeDB must not create a fake `.git` directory or require users to change
   global `project_root_markers`.
3. A trusted standalone Unity project remains a supported target independent of
   Git, SVN, Perforce, Package source, or the absence of version control.
4. Package installation and convergence must not require the user to create a
   Codex task as an installation step.
5. A real new Codex task created for the exact Unity project must expose the
   project namespace and complete `codedb_status` plus one bounded query before
   v0.3 release acceptance can pass.
6. Package-owned wrapper probing is necessary evidence, but it cannot replace
   real Codex client tool injection.
7. External Codex and MCP processes remain user-owned and are never stopped by
   diagnosis, installation, recovery, or validation.

## Readiness And Manager Semantics

The implementation must retain separate internal evidence:

| Evidence | Meaning |
| --- | --- |
| Project configuration | The project-local TOML is valid, ownership-safe, and located on a supported Codex project-discovery path. |
| Package backend | The selected Package-owned wrapper completes initialize, exact tools/list, usable status, and a bounded query. |
| Codex client observation | A matching client connection has not been observed, connected successfully, or failed with current correlated evidence. |

`Codex client observation = not observed` is neutral. It must not prevent
`Ready`, because a user may not have created a Codex task yet. A known
unsupported discovery path or a current correlated client failure is not
equivalent to an unobserved client and must remain diagnosable.

The ordinary Manager surface continues to expose only `Starting`, `Ready`,
`Needs attention`, `Missing prerequisite`, and `Uninstalled`, with at most one
contextual primary action. Detailed evidence belongs in Diagnostics.

The MCP page must not say `Project registration is current` solely because the
TOML and direct Package probe passed. Its user-facing wording should describe
the fact it actually proves, such as `Project configuration is ready`.
Diagnostics may separately show:

- project configuration: valid or invalid;
- Package backend: available or unavailable;
- Codex client: not observed, connected, or last correlated failure.

An unobserved client must not offer Reinstall. A correlated failure may expose
one contextual recovery action only when that action can repair the diagnosed
Package-owned cause.

## Phase 0: Read-only Root-cause Classification

Run all checks from the exact target project working directory and through the
same Codex host used by the new task. Do not invoke CodeDB MCP tools during the
initial classification.

1. Inspect `codex mcp list` and `codex mcp get codedb-test`.
2. Inspect bounded task-start/configuration diagnostics for the target server.
3. Determine whether the wrapper was never launched, launched and exited, or
   initialized without tool exposure.
4. Compare trusted project-root discovery in the standalone non-Git Unity
   project with the documented project-scoped configuration contract.
5. Record one of these outcomes before changing production code:

| Observation | Classification | Next boundary |
| --- | --- | --- |
| Server absent from active configuration | Project discovery/root/trust failure | Correct only the supported project-local discovery path. |
| Server present but never launched | Codex client MCP-loading failure | Identify the supported client trigger or external platform boundary. |
| Server launched and exited | Command/cwd/path/wrapper startup failure | Repair the narrow Package-owned startup cause. |
| Initialize/tools-list completed but tools are absent | Codex client injection failure | Preserve protocol evidence and isolate the client boundary. |

If official Codex behavior cannot support a trusted standalone non-Git project
without global mutation, stop and report an external platform blocker. Do not
hide that boundary with global registration or an undocumented workaround.

## Implementation Scope

After Phase 0 identifies the failing layer:

1. Make the smallest project-local functional correction required for that
   classification.
2. Keep the MCP server slug and expected namespace derived from the actual
   Unity project rather than hard-coding `codedb-project` or `codedb-test`.
3. Persist only bounded, current, Package-owned client-observation evidence;
   stale observations must not change the current product state.
4. Update the single product-state reducer and Manager presentation so
   configuration, backend availability, and client observation are not
   conflated.
5. Preserve unrelated TOML bytes, comments, order, legal descendant tables,
   BOM/EOL, ownership checks, atomic publication, rollback, and idempotency.
6. Preserve the selected instance/control, Supervisor, Play-transition, and
   external-process safety contracts.

## Focused Validation

Use a narrow layered gate for this task:

1. L0: syntax, package boundary, dynamic slug/namespace derivation, and
   `git diff --check`.
2. Focused EditMode: product-state reduction and user-facing/diagnostic MCP
   presentation for valid, invalid, unobserved, connected, and correlated
   failure evidence.
3. Focused integration: project TOML preservation and Package-owned wrapper
   initialize/tools/status/query behavior.
4. One final real Codex acceptance from a clean standalone non-Git Unity
   project with no user-global CodeDB registration:
   - confirm the exact project working directory;
   - confirm the expected `mcp__<project-slug>__*` namespace;
   - call the project `codedb_status`;
   - run one bounded project text query.

Do not rerun the complete materializer or full Unity matrix after every small
change. Run broader v0.3 regression once at the next frozen integration
snapshot. A direct wrapper probe, an older task, a different working directory,
or an unrelated global CodeDB namespace cannot satisfy the final acceptance.

## Definition Of Done

- A trusted standalone non-Git Unity project is discovered through its
  project-local Codex configuration without global CodeDB registration.
- A real new Codex task exposes the expected project namespace and passes
  usable status plus one bounded query.
- Manager wording no longer claims client registration from static
  configuration or direct wrapper evidence.
- Absence of a client observation remains neutral, while current correlated
  failures remain diagnosable and actionable without exposing internal phases
  on the ordinary user surface.
- No external process is stopped and no unrelated user or project
  configuration is changed.

## Non-goals

- user-global CodeDB registration;
- fake Git roots or global Codex root-marker changes;
- migration to a plugin-provided MCP server;
- requiring a Codex task before Package installation can complete;
- a broad Manager redesign or Supervisor refactor;
- theoretical TOML expansion or unrelated lifecycle hardening;
- released-artifact and third-party golden-path acceptance before this P0 is
  closed in the local development snapshot.
